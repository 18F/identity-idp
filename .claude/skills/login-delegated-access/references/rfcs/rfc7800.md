# RFC 7800 — Proof-of-Possession Key Semantics for JWTs (the `cnf` claim)

RFC 7800 defines the `cnf` (confirmation) claim: a way for a token, or a statement about a token,
to name the key whose possession a presenter must demonstrate. In this repository `cnf` appears
in the RFC 7662 introspection response for a key-bound delegated token, carrying the RFC 7638
thumbprint under the `jkt` confirmation method that RFC 9449 §6.1 registers. The agency API uses it
to check the DPoP proof on each request it receives. Canonical text: https://www.rfc-editor.org/rfc/rfc7800.txt

## Sections this implementation relies on

- **§3.1 Confirmation claim.** The `cnf` claim is a JSON object whose members
  identify the proof-of-possession key; a token with `cnf` is intended to be used only by a party
  that can demonstrate possession of that key. `OpenidConnectIntrospectForm#token_members`
  (`app/forms/openid_connect_introspect_form.rb`) adds `cnf: { jkt: <thumbprint> }` when the live
  entry's `dpop_jkt` is present. Companion INT-4 as amended, Appendix C "How it is built".
- **§3.2 to §3.5 Confirmation methods (`jwk`, `jwe`, `kid`, `jku`).** RFC 7800 defines these
  members; §6.2 (IANA) opens a registry so that other specifications can add methods. Only the
  registered `jkt` method (RFC 9449 §6.1) is used here; the full key is never returned.
- **§3.6 Specifics intentionally not specified.** RFC 7800 leaves the possession check to the
  application protocol. Here that protocol is RFC 9449: `DpopProofVerifier`
  (`app/services/dpop_proof_verifier.rb`) is the possession check at Login.gov's own endpoints,
  and companion §6.3 item 11 states the agency's obligation to perform the same check against `cnf.jkt`.
- **§4 Security considerations.** A `cnf` key must be bound to the token by a trusted issuer; the
  presenter must prove possession with a signature over something fresh. The binding here is written
  at issuance (`OpenidConnectTokenExchangeForm#create_issuance_record!`, `dpop_jkt:`) and reported
  only from Login.gov's own store (`DelegatedTokenStore.read`); freshness comes from the proof's
  `iat`, `jti`, `htm`, `htu` and `ath` (RFC 9449 §4.3).

## Deliberate choices and deviations

- **`cnf` is reported, never embedded.** Delegated tokens are opaque references (D29, EXC-20), so
  there is no JWT to carry `cnf`; introspection is the only place the agency learns the binding.
- **Thumbprint, not key.** `cnf.jkt` carries the RFC 7638 thumbprint; the agency gets the public
  key from the `jwk` header of each proof and compares thumbprints (RFC 9449 §4.3 item 12).
- **Present only when bound.** A confidential client's bearer token has no `cnf` (`token_type:
  Bearer`); a public client's token always has one (`token_type: DPoP`), because binding follows the
  client type (D47, EXC-17).
- **The SAML counterpart is an attribute.** A key-bound SAML assertion carries the thumbprint as a
  plain `dpop_jkt` attribute (`DelegatedSamlAssertion#delegation_attributes`,
  `app/services/delegated_saml_assertion.rb`), since RFC 7800 and RFC 9449 are JWT and OAuth
  constructs (E30, flagged for confirmation with the first SAML agency).
- **The service provider's own introspection also sees `cnf`** (INT-14) so a browser client can
  confirm which key its token is bound to.

## Questions this digest answers

- What does `cnf` look like in an active response? `"cnf": {"jkt": "<43 base64url chars>"}`.
- When is it absent? For bearer tokens (confidential clients) and for inactive tokens.
- Does `cnf` prove the caller holds the key? No; it names the key. The DPoP proof on the request proves possession.
- Is `jkt` defined in RFC 7800? No; RFC 9449 §6.1 registers it in the RFC 7800 confirmation-methods registry.
- Where is the thumbprint written? `token_exchange_tokens.dpop_jkt` at exchange, copied at every refresh.
- What must an agency do with `cnf.jkt`? Require the `DPoP` scheme and verify every request's proof against it (companion §6.3 item 11).
