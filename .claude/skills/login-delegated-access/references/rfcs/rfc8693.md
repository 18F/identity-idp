# RFC 8693 — OAuth 2.0 Token Exchange

RFC 8693 defines a security token service at the OAuth token endpoint: a client presents a token
it holds (`subject_token`) and receives a token for a target service, possibly in a different
format. It is the protocol of Login.gov's delegated access: a service provider exchanges the access
token of a person's sign-in for an opaque access token or a SAML 2.0 assertion scoped to one
agency API. The `act` claim it defines is how an agency learns that a service provider, not the
person, is calling. Canonical text: https://www.rfc-editor.org/rfc/rfc8693.txt

## Sections this implementation relies on

- **§1.1 Delegation vs. impersonation.** In delegation the token names both the subject and the
  actor. Every delegated token here is a delegation token: the person is `sub`, the service
  provider is `act.sub` (`OpenidConnectIntrospectForm#resource_server_response`,
  `app/forms/openid_connect_introspect_form.rb`) or the SAML `actor` attribute. Chained delegation
  is a non-goal: a delegated token can never be a `subject_token`
  (`OpenidConnectTokenExchangeForm#validate_subject_token`, EXC-6).
- **§2.1 Request.** `grant_type` REQUIRED (`urn:ietf:params:oauth:grant-type:token-exchange`);
  `subject_token` and `subject_token_type` REQUIRED; `resource`, `audience`, `scope`,
  `requested_token_type`, `actor_token` OPTIONAL; client authentication per RFC 6749.
  `OpenidConnectTokenExchangeForm#validate_request_shape` (`app/forms/openid_connect_token_exchange_form.rb`)
  requires `subject_token_type=urn:ietf:params:oauth:token-type:access_token`, a non-empty
  `subject_token`, exactly one `resource`, and accepts `requested_token_type` only when it is one of
  the two formats Login.gov issues. `OpenidConnect::TokenController#build_form` dispatches the grant
  (EXC-1; D30, D70).
- **§2.2.1 Successful response.** `access_token` REQUIRED (the issued token whatever its format),
  `issued_token_type` REQUIRED, `token_type` REQUIRED (`N_A` when the token is not usable as an
  OAuth access token), `expires_in` RECOMMENDED, `scope` and `refresh_token` OPTIONAL.
  `OpenidConnectTokenExchangeForm#response` returns all of them; `#issued_token_type_for` yields
  `N_A` for a SAML assertion and `DPoP` or `Bearer` otherwise (EXC-7, SAML-2, E15).
- **§2.2.2 Error response.** RFC 6749 §5.2 codes, plus `invalid_target` when the server is unwilling
  or unable to issue a token for the target named by `resource` or `audience`.
  `#validate_resource` fails with one wording for an unknown, inactive or excluding resource
  (`invalid_target`); `#validate_request_shape` uses `invalid_request` (EXC-3; D31, E26).
- **§3 Token type identifiers.** `urn:ietf:params:oauth:token-type:access_token` and
  `urn:ietf:params:oauth:token-type:saml2` (a base64url-encoded SAML 2.0 assertion).
  `OpenidConnectTokenExchangeForm::REQUESTED_TOKEN_TYPES`; `DelegatedSamlAssertion#encoded`
  (`app/services/delegated_saml_assertion.rb`) returns the bare assertion base64url without padding.
- **§4.1 `act` claim.** Identifies the acting party; nested `act` expresses a chain; a consumer
  treats the current actor as the party acting. Introspection returns `act: { sub: <service
  provider issuer> }` to the agency and omits it for the service provider (INT-4, INT-14). §4 also
  says these claims may appear in an RFC 7662 introspection response, which is how they are used here.
- **§4.3 `client_id` claim.** The client that requested the token. Introspection's `client_id` is the
  service provider's issuer (`#token_members`).

## Deliberate choices and deviations

- **`requested_token_type` is optional and does not decide the format** (D70, E109). The resource
  server's registered `token_format` decides (`TokenExchangeResourceServer#saml?`); a sent value
  naming the other format is served in the registered format, `issued_token_type` states it and
  `requested_token_type_mismatch` is logged. A value that is neither URN is `invalid_request`.
- **Exactly one `resource`** (D30); two or more is `invalid_request` although RFC 8707 permits
  several. One token has one audience.
- **`audience` and `actor_token` are not read.** The actor is the authenticated client; `aud` is
  the resource identifier.
- **Subject-token problems are `invalid_grant`, not `invalid_request`.** §2.2.2 directs
  `invalid_request` for an invalid subject token; this implementation reserves `invalid_grant` for a
  foreign, revoked, session-less or unverified subject token so a service provider can tell "fix the
  request" from "sign the person in again" (companion §5 "Errors", E26).
- **`consent_required`** (OpenID Connect Core §3.1.2.6) is returned, naming the scope to request,
  when the authenticated caller names a registered resource the person has not approved (D31).
- **A live sign-in is required for the first exchange** (D28, E2, E64); RFC 8693 is silent on
  subject-token freshness. The family then runs independently (RFC 6749 §6).
- **`scope` on the request is ignored** (D72, E111). **No `id_token`** is ever issued (EXC-5).
- **Refresh tokens are issued** (§2.2.1 permits them) and rotate per RFC 9700.

## Questions this digest answers

- Which endpoint serves the exchange? The existing token endpoint; RFC 8693 defines no endpoint of its own (DISC-3).
- What is `token_type` for a SAML assertion? `N_A` (§2.2.1), whatever the client type.
- Can I pass two `resource` values? No; `invalid_request` (D30).
- What happens if I request `saml2` for an `oauth` API? You receive the OAuth token; check `issued_token_type` (D70).
- Why `invalid_target` rather than "unknown resource"? §2.2.2; one wording keeps the endpoint from describing the registry.
- Why `invalid_grant` for a subject token the RFC would call `invalid_request`? Deliberate (E26); see above.
- Is a delegated token exchangeable again? No; it is not an `identities` row and is refused as `subject_token` (EXC-6).
- Where does the agency see `act`? Only in introspection (or the SAML `actor` attribute), never in a token string.
