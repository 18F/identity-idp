# RFC 7636 — Proof Key for Code Exchange (PKCE)

RFC 7636 protects the authorization code of a public client: the client sends a hashed
`code_challenge` on the authorization request and the matching `code_verifier` when redeeming the
code. In this repository PKCE is how a browser-based service provider redeems its own
authorization code; it is deliberately not accepted as a credential on the delegated-access grants,
where key binding (RFC 9449) plays that role. Canonical text: https://www.rfc-editor.org/rfc/rfc7636.txt

## Sections this implementation relies on

- **§4.1 Client creates a code verifier.** A high-entropy string of 43 to 128 characters from the
  unreserved set `[A-Z] [a-z] [0-9] - . _ ~`. `OpenidConnectTokenForm#valid_code_verifier?`
  (`app/forms/openid_connect_token_form.rb`) enforces exactly this format for the
  `private_key_jwt` plus PKCE path; existing PKCE integrations keep their earlier validation.
- **§4.2 Client creates the code challenge.** `S256`: `BASE64URL(SHA256(ASCII(code_verifier)))`,
  unpadded. `OpenidConnectAuthorizeForm::BASE64URL_SHA256_FORMAT` (`app/forms/openid_connect_authorize_form.rb`)
  is the 43-character shape of that value (shared with the RFC 7638 thumbprint check);
  `code_challenge_method` is restricted to `S256`.
- **§4.3, §4.4 Client sends the challenge; server associates it with the code.**
  `OpenidConnectAuthorizeForm#validate_pkce_parameter_pair` requires `code_challenge` and
  `code_challenge_method` together; the challenge is stored on the identity row for the code.
- **§4.5, §4.6 Client sends the verifier; server verifies.** The server transforms the verifier
  and compares it with the stored challenge; a mismatch is an `invalid_grant` error (RFC 6749 §5.2).
  `OpenidConnectTokenForm#validate_code_verifier` and `#code_verifier_matches_challenge?` compute
  the S256 digest and compare with `ActiveSupport::SecurityUtils.secure_compare`; `#response`
  reports `invalid_grant` with `invalid_code_verifier` for the `private_key_jwt` plus PKCE path.
- **§7.2 Protection against eavesdroppers.** Clients MUST NOT downgrade to `plain`. Only `S256` is accepted.

## Deliberate choices and deviations

- **PKCE is not a client credential on the delegated grants.** `DelegatedAccessClientHandling#validate_code_verifier_absent`
  (`app/forms/concerns/delegated_access_client_handling.rb`) fails any exchange, refresh or
  revocation that carries `code_verifier` with `invalid_request`. Rationale: companion EXC-2
  (confidential clients authenticate with RFC 7523; public clients prove key possession with RFC 9449).
- **A public client approved for delegation gets PKCE plus key binding.** PKCE still protects the
  code against interception; `dpop_jkt` (RFC 9449 §10) additionally binds the code to the client's
  key so the issued tokens are useless outside the browser that holds the key (EXC-19, D21).
- **`client_id`-only clients are the `pkce: true` records.** Client type is fixed at onboarding;
  the `pkce` flag on the service provider record is what `DelegatedAccessClientHandling` reads to
  decide which credential to expect (companion §5.5).

## Questions this digest answers

- Can a confidential client send `code_verifier` on the token-exchange grant? No; `invalid_request` (EXC-2).
- Which challenge method is supported? `S256` only.
- What length must `code_verifier` be? 43 to 128 unreserved characters (§4.1), enforced on the `private_key_jwt` plus PKCE path.
- Why does a bad verifier return `invalid_grant` and not `invalid_request`? §4.6 names `invalid_grant`.
- Does PKCE alone protect the public client's tokens? No; it protects the code. The tokens are protected by DPoP binding (RFC 9449).
- Where is the challenge format shared with DPoP? `OpenidConnectAuthorizeForm::BASE64URL_SHA256_FORMAT`, used for both `code_challenge` and `dpop_jkt`.
