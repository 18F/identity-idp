# RFC 7523 — JWT Profile for OAuth 2.0 Client Authentication (`private_key_jwt`)

RFC 7523 defines how a client authenticates to the token endpoint (and, by extension, to any
endpoint that accepts RFC 6749 client authentication) with a signed JWT. In this repository it is
the credential of every server-to-server caller: a confidential service provider at exchange,
refresh and revocation, and an agency API at introspection. OpenID Connect Core §9 names this
method `private_key_jwt`. Canonical text: https://www.rfc-editor.org/rfc/rfc7523.txt

## Sections this implementation relies on

- **§2.2 Using JWTs for client authentication.** The request carries
  `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` and
  `client_assertion` holding the JWT. `DelegatedAccessClientHandling#authenticate_confidential_client`
  (`app/forms/concerns/delegated_access_client_handling.rb`) checks the type
  (`OpenidConnectTokenForm::CLIENT_ASSERTION_TYPE`) and hands the assertion to
  `ResourceServerAuthenticator` (`app/services/resource_server_authenticator.rb`).
- **§3 item 1, 2: `iss` and `sub`.** The JWT MUST contain `iss`; for client authentication `sub`
  MUST be the `client_id`. `ResourceServerAuthenticator#unverified_issuer` reads `iss`, requires
  `iss == sub`, and uses it to find the record whose keys verify the signature
  (`#find_record`, `key_source:` `:service_provider` or `:resource_server`); `#verify_signature`
  then verifies `iss` and `sub` again under the signature. Companion EXC-2, INT-1, INT-6.
- **§3 item 3: `aud`.** The JWT MUST contain `aud` identifying the authorization server; the token
  endpoint URL MAY be used. `#audience_matches?` requires one `aud` value equal to the URL of the
  endpoint being called (trailing slash ignored); each form supplies it through
  `client_assertion_audience` (token, revoke or introspect URL), so an assertion for one endpoint
  cannot be replayed at another.
- **§3 item 4: `exp`.** The JWT MUST contain `exp` and MUST be rejected when expired; the server MAY
  allow skew. `REQUIRED_CLAIMS` includes `exp`; `#lifetime_acceptable?` further caps `exp` at
  `MAX_LIFETIME_SECONDS` (300) after `iat` (or after now when `iat` is absent) plus
  `ISSUED_AT_LEEWAY_SECONDS` (10). INT-6.
- **§3 item 6: `iat`.** OPTIONAL. `#issued_at_acceptable?` accepts an absent `iat` and refuses one
  more than ten seconds in the future.
- **§3 item 7: `jti`.** OPTIONAL in RFC 7523; the server MAY use it to detect replay. Here it is
  required (OpenID Connect Core §9 requires it for `private_key_jwt`) and single-use:
  `#first_use_of_jti?` records it through `ReplayGuard.first_use?` (`app/services/replay_guard.rb`)
  under the caller's identifier for the maximum lifetime plus leeway, after the signature verified.
- **§3 item 9, 10 and §3.2: signature and rejection.** The JWT MUST be signed and MUST be rejected if
  the signature is invalid. `#verify_signature` pins `RS256` and tries every certificate on the
  record so key rotation does not break callers; failures are `invalid_client` (RFC 6749 §5.2).

## Deliberate choices and deviations

- **Stricter than the authorization-code grant.** `OpenidConnectTokenForm#validate_client_assertion`
  (`app/forms/openid_connect_token_form.rb`) checks only signature, `iss`/`sub`, `aud` and a
  non-future `iat`; the delegated endpoints add required `exp` and `jti`, a five-minute lifetime and
  replay detection because machines call them thousands of times a day (companion §6.1 "Why INT-6").
  The existing form is left as is so current integrations are unaffected.
- **Algorithm pinned to RS256**; the `alg` header is never trusted (RFC 8725 §3.1). Discovery
  advertises `RS256` only for `token_endpoint_auth_signing_alg_values_supported` and the
  introspection and revocation equivalents (`OpenidConnectConfigurationPresenter`).
- **`iss`/`sub` read unverified first** to select the keys, then verified. Nothing from that read is
  trusted except the record lookup (`#unverified_issuer` comment).
- **Signature before replay cache**, so an anonymous party cannot burn a legitimate caller's `jti` values.
- **Not accepted from a public client.** An assertion from a `pkce: true` record is `invalid_client`
  (`client_type_mismatch`): the two credentials are not interchangeable (EXC-2 as amended).

## Questions this digest answers

- What must `aud` be? The absolute URL of the endpoint being called; a token-endpoint assertion fails at `/introspect`.
- Is `jti` required? Yes, and it is single-use for 310 seconds per caller.
- How long may an assertion live? At most 300 seconds after `iat` (plus 10 seconds leeway).
- Which keys verify an agency's assertion? The certificates on its `TokenExchangeResourceServer` record (`key_source: :resource_server`).
- Can an assertion name a different `sub` than `iss`? No; `iss` must equal `sub` and both must be the registered identifier.
- Which error does a failed assertion produce? `invalid_client` (HTTP 400 at the token endpoint, 401 at revocation and introspection).
- Why does the same class serve service providers and agencies? Only the key source differs (`KEY_SOURCES`).
