# RFC 9700 — Best Current Practice for OAuth 2.0 Security

RFC 9700 updates RFC 6749's security guidance with the practices a modern deployment must follow:
PKCE for every client, sender-constrained tokens, and refresh-token rotation with reuse detection
for public clients. In this repository it is the basis of the refresh-token family model, the
"revoke the whole family on reuse" rule and the choice to bind the public client's tokens with DPoP.
Canonical text: https://www.rfc-editor.org/rfc/rfc9700.txt

## Sections this implementation relies on

- **§2.1.1 PKCE for the authorization code grant.** Public clients MUST use PKCE; servers MUST
  support it. The public-client service provider is a `pkce: true` record and
  `OpenidConnectTokenForm` (`app/forms/openid_connect_token_form.rb`) verifies the `S256` verifier (RFC 7636).
- **§2.2, §4.10.1 Sender-constraining access tokens.** Access tokens SHOULD be sender-constrained
  (mTLS or DPoP) so a leaked token cannot be replayed. Every token issued to the public client is
  DPoP-bound (`DpopProofVerifier`, `app/services/dpop_proof_verifier.rb`; `AccessTokenVerifier`,
  `app/services/access_token_verifier.rb`). Companion Appendix C and EXC-17; D19–D22 of the baseline change, D47.
- **§4.14.2 Refresh token recommendations.** Refresh tokens for public clients MUST be either
  sender-constrained or rotated; with rotation the server issues a new refresh token on every
  refresh and, when an already-used token is presented, revokes the active refresh token (the
  family), since it cannot tell the legitimate client from the attacker. The server MUST bind refresh
  tokens to the client; refresh tokens of confidential clients are protected by client authentication.
  `TokenExchangeRefreshToken` (`app/models/token_exchange_refresh_token.rb`) is the rotating row;
  `OpenidConnectRefreshTokenForm#rotate_locked!` (`app/forms/openid_connect_refresh_token_form.rb`)
  marks the presented row `rotated_at` and mints the next; `#handle_reuse!` calls
  `TokenExchangeRefreshToken.revoke_family!` with reason `refresh_token_reuse` and reports it
  (`DelegatedAccessEvents.access_revoked`). REF-4 as amended; D33.
- **§4.14.2 (continued) Both at once for public clients.** Here a public client's refresh tokens are
  both bound (`dpop_jkt` on the row, `#validate_refresh_token` requires the proof key) and rotated;
  a confidential client's are rotated and protected by `private_key_jwt`.
- **§4.4 Mix-up attacks, §4.10.2 Audience-restricted access tokens.** Tokens are audience-restricted to one resource (RFC 8707) and
  client assertions name the exact endpoint in `aud` (RFC 7523), so a credential or token minted for
  one endpoint or API is refused at another.
- **§4.8 PKCE downgrade attack.** Only `S256` is accepted and PKCE is never a substitute for a
  client credential (`DelegatedAccessClientHandling#validate_code_verifier_absent`).

## Deliberate choices and deviations

- **Reuse revokes the whole family**, not just the presented token (D33): a stolen token must cost
  its holder the access rather than extend it. A family already revoked is not revoked or reported
  again, so one theft is reported once (REF-10).
- **Rotation runs under a row lock** (`TokenExchangeRefreshToken.lock.find`), so two concurrent
  refreshes cannot both succeed; the second sees the row spent and is treated as reuse (REF-10).
- **Absolute family lifetime of 12 hours** from the exchange that opens it, never past the approval's
  `remember_until`, shortened by per-API and per-service-provider limits (`TokenExchangeRefreshToken.family_end`;
  D32, D61). RFC 9700 does not fix a figure; the 12-hour AAL2 reauthentication ceiling of
  NIST SP 800-63B §4.2.3 is the rationale (companion §7.1 "Why 12 hours").
- **Access tokens live 15 minutes** by default (`token_exchange_access_token_ttl_seconds`, 900),
  shorter per API, never longer, and never past the family end (`TokenExchangeToken.lifetime_seconds_for`; D27, REF-12).
- **A lapsed approval ends the family at the next refresh** (`approval_lapsed`), while a kill switch
  only refuses, so switching an API back on restores the family (`#rotate_locked!`).
- **Only digests are stored** (REF-7); the plaintext exists in the token response alone.
- **Reuse is logged for operations** (`delegation_refresh_token_reuse` analytics) and reported to the
  agency through the Attempts API, without any per-caller rate limit (D37).

## Questions this digest answers

- What happens if I present a refresh token twice? The second presentation revokes the whole family (`invalid_grant`, `refresh_token_reused`); exchange again.
- Does a refresh extend the family? No; the family end is absolute (D32).
- Why does the second of two parallel refreshes fail? Rotation is serialized by a row lock; the second sees the token spent.
- Are confidential clients' refresh tokens rotated too? Yes; rotation applies to every family, binding only to public clients.
- Can a refreshed access token outlive the family? No; `lifetime_seconds_for` caps it at the family end.
- Which section justifies DPoP for the public client? §4.10.1 (sender-constraining) with RFC 9449.
- Does a password change or suspension revoke families? Suspension and deletion do (`TokenExchangeGrant.revoke_all_for_user!`); sign-out does not (REF-6).
