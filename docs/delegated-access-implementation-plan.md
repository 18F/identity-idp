## 3. The foundation (`sbx-taigrr`) and the architecture layered on top (`token-exchange2-login`)

`sbx-taigrr` is the foundation the project builds on; the additional architectural components come from `token-exchange2-login`, layered on top of that foundation. This section describes each in turn and where the layered components touch the same files as the foundation.

### 3.1 The foundation: `sbx-taigrr`

The branch is the `token-exchange` branch plus later commits (target opt-in, per-application grants, account-page toggles), merged with a `proofing/socure-identity-artifacts` branch that adds identity-document image and metadata sharing. It is the base the rest of the project is built on.

Its original design differs from the functional requirements rather than being a partial implementation of them, which is why the later architecture is layered on top rather than merely finished. Its design document (`docs/token-exchange.md`) describes a **browser-callable** RFC 8693 exchange, **with no client secret**, that mints a **full user access token for the target service provider**, structurally identical to one the user would have received by signing in there directly, whose lifetime is the service provider's Rails session. Consent is per *application the user has already connected to*, not per agency API the service provider requests. The `document_images` scope lets an allow-listed service provider download the ID document photos and the selfie over a bearer-token URL and read the document number and dates from userinfo. The branch calls the service provider the "broker" in code, comments, strings and its design document; this document says *service provider*, and every identifier that carries the old word is renamed or removed by the feature that touches it (5.1, 5.2, 5.3).

Components:

1. `POST /api/openid_connect/exchange` (`OpenidConnect::ExchangeController`, `OpenidConnectTokenExchangeForm`), with a CORS rule in `config/application.rb` so browsers can call it.
2. A `token_exchange` scope, honored only for service providers listed in the `token_exchange_service_providers` JSON key of `application.yml`, treated as an IAL2 attribute scope so it flows through `requested_attributes`.
3. Target opt-in: `service_providers.allowed_token_exchange_brokers` (string array column).
4. `token_exchange_grants` (one row per user, service provider issuer, target issuer; 12-month expiry; revoke-not-delete) and `token_exchange_broker_settings` (auto-enrollment of future targets).
5. Consent control on the existing completions screen: "allow across all linked agencies", "automatically enroll new agencies", or pick specific linked applications grouped by agency (client-side paginated).
6. Account page: per-application on/off toggles and an auto-enroll toggle under the service provider's connected-app entry, with a confirmation modal.
7. Billing: an `SpReturnLog` row for the target at mint, billable once per (user, target, service provider session) through a deterministic `request_id`.
8. Attempts API: one `token-exchange-login-completed` event to the target at mint, carrying `broker_issuer`.
9. `id_token` for the target carries an RFC 8693 `act` claim naming the service provider; no `nonce`, no `c_hash`.
10. `document_images` scope, `document_artifacts` and `document_metadata` tables, `GET /api/openid_connect/document_images/:type` bearer-authenticated download, biometric consent checkbox on the completions screen, `ExpireDocumentArtifactsJob`, two design documents under `docs/proofing/`.

### 3.2 Layered on top: `token-exchange2-login`

The additional architectural components layered onto the foundation come from `token-exchange2-login`: forty-one commits (160 files, about 11,800 lines added, 326 new spec examples) implementing the requirements document end to end against `main` at `48a1ff3e3f` (2026-09-04): onboarding data model, `token_exchange:<name>` scopes and the agency-level consent screen, Account → Delegated access, RFC 8693 exchange at the existing token endpoint with `private_key_jwt`, opaque delegated tokens with refresh rotation and RFC 7009 revocation, RFC 7662 introspection authenticated by the agency, Attempts buffering and delivery, billing rows and reports, SAML assertions as an issued token type, DPoP, discovery metadata, suspension and deletion cascade. It has only ever run locally, with the three reference applications and the live end-to-end harness (24 scenarios passing on 2026-10-08).

### 3.3 Where the layered components touch the foundation

Twenty-eight files are changed by both branches relative to their bases. A dry-run merge of `token-exchange2-login` into `sbx-taigrr` conflicts in seventeen: `app/forms/openid_connect_token_exchange_form.rb` (both add it), `app/forms/openid_connect_token_form.rb`, `app/models/token_exchange_grant.rb` (both add it), `app/presenters/openid_connect_user_info_presenter.rb`, `app/services/analytics_events.rb`, `app/views/accounts/_connected_app.html.erb`, `app/views/sign_up/completions/show.html.erb`, `config/application.yml.default`, `config/initializers/job_configurations.rb`, the four locale files, `config/routes.rb`, `db/schema.rb`, `lib/identity_config.rb`, `spec/models/token_exchange_grant_spec.rb`. The branch is therefore built by porting, not merging.

Name collisions that must be resolved deliberately, because the same name means different things on the two branches:

1. **Table `token_exchange_grants`.** `sbx-taigrr`: `(user_id, broker_issuer, target_issuer, granted_at, expires_at, revoked_at)`, one row per application. `token-exchange2`: `(identity_id, token_exchange_scope_id, delegation_id, status, scope_content_version, sp_content_version, consented_at, remember_until, rails_session_id, proofed_in_session, first_exchanged_at, revoked_at, revocation_reason)`, one row per consent decision per API. The decided shape (section 9, D8) is one row per (user, service provider, application), closer to `sbx-taigrr`'s key with new columns. The sandbox database already has `sbx-taigrr`'s table, so the new branch's first migration drops it before creating the new one (nothing is kept for compatibility; neither branch is in production).
2. **Class `TokenExchangeGrant`** and **class `OpenidConnectTokenExchangeForm`**: different responsibilities on each branch.
3. **Scope string.** `sbx-taigrr` uses the bare scope `token_exchange` as an IAL2 attribute; `token-exchange2` uses `token_exchange:<scope_value>` per API. The bare value never matches the prefixed form, so the two could coexist, but the bare scope's side effect (it is written to `identities.verified_attributes`) is the cause of the remembered-decline bug below and must go.
4. **Config key `token_exchange_enabled`**: same meaning on both (master switch). Keep.
5. **Config key `token_exchange_service_providers`** (`sbx-taigrr`, JSON allow-list of service providers) against column `service_providers.token_exchange_enabled_sp` (`token-exchange2`). FR-ONB-9 and §3 ONB-5 require the SP-configuration path. Decision in 5.1.
6. **Analytics event `openid_connect_token_exchange`**: both define it with different properties.
7. **Attempts event `token-exchange-login-completed`** (`sbx-taigrr`) against the delegated event family in `token-exchange2` (`delegation-consented`, `delegated-token-issued`, `delegated-token-refreshed`, `delegated-access-revoked`, with `delegation_id`).
8. **Locale keys** `sign_up.token_exchange_grant.*` and `account.connected_apps.token_exchange.*` (`sbx-taigrr`) against `sign_up.delegation.*` and `account.delegated_access.*` (`token-exchange2`).
9. **`ServiceProvider#token_exchange_broker_allowed?` / `#allows_token_exchange_broker?`** against `#delegation_service_provider?` and the resource-server associations.

### 3.4 What the foundation contributes regardless of feature

These pieces of the foundation do not conflict with the premise of any requirement and are kept, in some cases generalized:

1. **Agency opt-in to specific service providers** (`allowed_token_exchange_brokers`). It answers the open question in functional requirements section 3, question 3 ("should an agency be able to restrict which service providers may use its APIs"). It moves from "target SP" to "agency SP that owns resource servers" and is enforced at authorize (FR-CEN-2) and at exchange.
2. **IAL forwarded, never elevated** (FR-FIT-5). `token-exchange2` copies `ial` and `aal` onto the delegated token; the same rule.
3. **The `act` claim naming the service provider** (FR-VER-3). `token-exchange2` returns it from introspection and as a SAML attribute.
4. **Analytics on every decision** (FR-OPS-2), renamed to the new vocabulary.
5. **Refusing to describe target-side errors until the caller has cleared its own gates** (audience probing). Carried into the exchange form.
6. **Document image and metadata sharing for a service provider the user signs in to directly** (section 5.12). It is a separate feature with its own flag and allow-list and is left in place.
7. **mDL exemption** for image sharing.
8. **Per-application toggles on the account page.** The pattern (a toggle per application under the service provider, confirmation before turning one on) is kept; what changes is the list, which becomes every registered application that accepts the service provider rather than the applications the user has connected to (section 9, D4).
9. **One consent choice per application, grouped by agency.** `sbx-taigrr`'s screen already works at application granularity, which is the granularity decided on 2026-10-09 (D1); the functional requirements move from agency-level to application-level consent.

## 4. Approach for `login-delegated-access`

1. Start from `sbx-taigrr` `0b0539e19`, merge `main`, then add features in the order of section 5. Each feature is one worktree and one branch (`lda-NN-<name>`), stacked on the one before it (section 8), and fast-forwarded into `login-delegated-access` when accepted.
2. Add only what a feature's functional requirements need. Remove only what contradicts the premise of that feature, and say so in the commit message in plain terms (for example: "the exchange is server-to-server, so the browser-callable endpoint and its CORS rule are removed").
3. Port from `token-exchange2-login` wherever the piece was tested there: models, forms, services, specs. Porting is by hand (the files conflict), commit by commit where a commit is self-contained. Comments stay functional and cite RFC sections, never requirement identifiers; this document carries the FR mapping instead.
4. **The service provider is a public client, and every token it holds is key-bound.** A browser-based service provider cannot keep a client secret, so it signs in with PKCE and, to keep a stolen token useless, binds its tokens to a key it holds in the browser with DPoP (RFC 9449): its own access token (the subject token of the exchange), the delegated tokens, and the refresh tokens that renew them. Login.gov verifies a proof from that key at the code exchange, the token exchange, refresh, and at userinfo for the service provider's own token; a bound token presented as a plain bearer token is refused. Delegated tokens are never accepted at userinfo at all: an agency's attributes reach only the agency, through introspection, and the agency verifies the proof on the API call. This applies only to service providers approved for delegation that are public clients; every existing confidential-client integration keeps `private_key_jwt` and bearer tokens and does not change. How the service provider protects the key inside its own page (CSP, non-extractable keys) is a client-side implementation and out of scope here. (Baseline changed 2026-10-09; see section 9, D19 to D22. The earlier confidential-client wording is withdrawn.)
5. **Terminology.** *Service provider*, never "broker", for the application the user signs in to; *resource server* or *agency API* for the target; *agency SP* for the agency's record. Identifiers, strings, comments and analytics properties that say "broker" are renamed or removed by the feature that owns them.

   Within identity-idp the application that requests delegated tokens is a `ServiceProvider` record (with delegation enabled), so this repository keeps calling it the *service provider*; its model, columns, config keys (`token_exchange_enabled_sp`, `allowed_delegation_service_providers`) and analytics stay on that word, which is the house term every relying party shares. The reference applications outside this repository name roles from their own side: the browser public client (GSA-TTS/identity-sts-sinatra) calls its own role the *client broker* so it is not confused with Login.gov's generic service-provider record, and the agency reference APIs call the delegated-token caller the *broker* (except where SAML's own "service provider" protocol role is meant). That client-side renaming does not reach back into identity-idp's code or wire contract.
6. **Names.** No real-world service provider or agency appears in code, fixtures, comments, strings or this plan. The fixtures use the fictitious names the design documents already use (MyBenefits Assistant, Office of Benefits Coordination, Department of Housing Support, National Retirement Administration); everywhere else the role name or the RFC term is used.
7. **No compatibility code.** Neither `sbx-taigrr` nor `token-exchange2` is in production. Nothing is kept, renamed to `legacy` or `old`, or left behind a flag because it might be depended on. Each feature decides what stays and what goes, and removes what goes.
8. **Local before CI.** Every feature runs locally first: its specs, and from 5.4 on the end-to-end harness against the local IdP and reference applications. Nothing is pushed to GitLab (which starts a pipeline and a review app on any branch) until that has happened.
9. The three documents in `docs/` (this plan, the functional requirements, the requirements document) are updated in the same change as the code or decision they describe, never later; they are the authoritative copies.
10. **Comments describe the code as it is.** No design history ("previous design", "kept for compatibility") and no forward references ("feature X replaces this later") in code, migrations or comments; that context lives in this document and may go in commit messages. Stating a present external dependency (for example that the Dashboard lacks a field and a seed task fills in) is fine.
11. **Content is configuration.** The agencies' consent content, the agency applications' names, consent text, logos and API URLs, and the service providers approved for delegation are maintained as YAML in the shared configuration repository (`18F/identity-idp-config`, `delegated_access.yml`), reviewed by pull request and seeded by `rake db:seed` in every environment, exactly as `service_providers.yml` and `agencies.yml` are. No admin interface is built for it (D77; 5.17). The Dashboard remains the longer-term path (6.2).

## 5. Features, in dependency order

Each feature lists: the functional requirements it serves; what `sbx-taigrr` has; what is added; what is removed and why; findings for engineering decisions; what to port from `token-exchange2-login` (commit shas on GitLab `lg/identity-idp`); its worktree; what it depends on. A feature never depends on a later one.

### 5.1 Onboarding data model and configuration

**Worktree** `delegated-access-registry`. **Depends on** section 2 (main merged). **Decisions:** section 9, D1–D3, D7–D12.
**Requirements:** FR-ONB-1 to FR-ONB-9, FR-OPS-1; companion §3 (ONB-1..8 as amended in §3.4), §10.

**The model as decided.** An *application* is an agency's service provider record (one `service_providers` row the agency owns), extended with consent content and owning one or more *resource servers* (the application's API URLs). The person consents per application. The service provider requests one delegation scope per application, `token_exchange:<application scope value>`; the application's URLs are shown for information and `resource` selects one of them at exchange. Agency-level content (what the agency says about itself) lives on `agencies`.

**What `sbx-taigrr` has.** A service provider allow-list in `application.yml` (`token_exchange_service_providers`), a target opt-in column (`allowed_token_exchange_brokers`), two feature flags (`token_exchange_enabled`, `document_images_sharing_enabled`), and the two grant tables. Its targets are whole service providers, which is the application granularity decided on; what is missing is the URL registry under each application, the content, the versions, and the service provider approval on the SP record.

**Add.**
1. `agencies`: localized `delegation_description` (jsonb), `delegation_learn_more_url`, `consent_content_version`, `consent_material_version` (the version at which the last material change was made). FR-ONB-3, D9, D12.
2. `service_providers`, application role: `delegation_application` (boolean), `delegation_scope_value` (unique, `[a-z0-9_]{1,64}`, the part after `token_exchange:`), localized `delegation_display_name`, `delegation_description`, `delegation_data_provided`, `delegation_access_type` (`read`/`read_write`), `delegation_learn_more_url`, `consent_content_version`, `consent_material_version`, `consent_approved_at`/`consent_approved_by`, `allowed_delegation_service_providers` (string array; empty means any approved service provider). FR-ONB-2, FR-ONB-3, FR-ONB-5, FR-ONB-8, D1, D2, D7.
3. `service_providers`, service provider role: `token_exchange_enabled_sp`, operator legal name and type, localized service description, data-handling statement, AI description, `delegation_uses_ai`, privacy policy, terms and support contact, `sp_content_version`, `sp_material_version`. FR-ONB-1, FR-ONB-4, FR-ONB-6.
4. `token_exchange_resource_servers` as in `token-exchange2` (identifier URL, owning application, Attempts recipient SP, `billing_issuer`, `certs`, `token_format`, `dpop_required`, `active`): the application's URLs. FR-ONB-2, FR-ONB-7. The `dpop_required` column added by this migration is dropped by the DPoP feature's migration (5.10; D47): binding follows the service provider's client type, not the API, so the column and the seeder and localdev fixture key of the same name go with it. No `token_exchange_scopes` table: with one scope per application the scope value and content live on the application row.
5. `token_exchange_grants`, new shape: `user_id`, `service_provider_issuer`, `application_service_provider_id`, `delegation_id`, `source` (`consent_screen`/`account_page`), `consented_at`, `remember_until` (null for a single-sign-in grant), `rails_session_id` (single-sign-in grants only), `agency_content_version`, `application_content_version`, `sp_content_version`, `proofed_in_session`, `first_exchanged_at`, `revoked_at`, `revocation_reason`; one live row per (user, service provider, application). D4, D6, D8, D9. The model carries the validity rule (live, not revoked, remembered-and-current or current-authorization, every recorded content version at or above the owner's material version).
6. Seeder and updater: nested `token_exchange_resource_servers` under an application upserted by `identifier`, children deactivated when absent from a Dashboard payload; the new SP and agency columns pass through. FR-ONB-7, FR-ONB-9.
7. `IdentityConfig` keys with defaults: token and refresh TTLs, introspection cache seconds, three rate-limit pairs, `delegation_outcomes_report_emails`. Companion §10.
8. `config/delegated_access.localdev.yml` and `rake delegated_access:seed` (refuses `prod` and `staging`): the fictitious service provider (MyBenefits Assistant, Office of Benefits Coordination), two agencies with one application each (Department of Housing Support; National Retirement Administration), one OAuth and one SAML resource server, content for all of them. Used locally, in the review app and in a personal sandbox until the Dashboard carries the fields. D10. This file is the single fixture contract between the seed task and the `identity-sts-sinatra` end-to-end harness (D51; 5.11).
9. Explicit dependency notes, in code comments on the seeder, updater and models and in the requirements documents: the Dashboard (`identity-dashboard`) must gain the agency and application content fields, the service provider delegation fields, `allowed_delegation_service_providers` and nested resource servers in its API payload before partners can self-serve; `ServiceProviderUpdater` already reads that shape. D3, D10.
10. The migration that drops `sbx-taigrr`'s `token_exchange_grants`, `token_exchange_broker_settings` and `allowed_token_exchange_brokers`, and creates the above. Findings 1.
11. Full terminology sweep across the branch: every identifier, string, comment, analytics property and locale key that says "broker" says service provider; every comment describing the exchange as browser-callable or the service provider as a public client of Login.gov is corrected to the confidential-client baseline (section 4 item 4), including in code that later features will delete. D11.

**Remove, and why.**
1. `token_exchange_service_providers` from `application.yml`: approval to request delegation is partner configuration reviewed through the SP onboarding path (FR-ONB-9, ONB-5). Replaced by `service_providers.token_exchange_enabled_sp`. `token_exchange_enabled` stays as the master switch (FR-OPS-1). D7.
2. `token_exchange_broker_settings` and its model: auto-enrollment of future agencies conflicts with the registry-defined list the person chooses from (D4) and with FR-CEN-1. Pre-approval from the account page replaces the need.
3. `allowed_token_exchange_brokers`: replaced by `allowed_delegation_service_providers` on the application row with the same meaning and an "any approved service provider" default. D7.
4. The two localdev fixtures `urn:gov:gsa:openidconnect:sp:token_exchange_broker` and `…:token_exchange_target`: replaced by the seed file.

### 5.4 Server-to-server token exchange

**Worktree** `delegated-access-token-exchange`. **Depends on** 5.1, 5.2 (grants to check), 5.10 (the proof verifier and the key-bound sign-in token the exchange checks the proof against; D64).
**Requirements (as amended 2026-10-09):** FR-TOK-1, FR-TOK-2, FR-TOK-3, FR-TOK-4, FR-TOK-5, FR-TOK-6, FR-TOK-7, FR-TOK-8, FR-TOK-17, FR-TOK-19, FR-TOK-20 (exchange half), FR-TOK-21, FR-TOK-26, FR-CEN-8, FR-CEN-10, FR-CEN-12, FR-CEN-16; companion §5 (EXC-1..12 as amended in §5.5 and §5.6), §6.2 (authenticator). **Decisions:** section 9, D26–D31, D37.

**What `sbx-taigrr` has.** `POST /api/openid_connect/exchange`, no CSRF, no client authentication, a CORS rule for browsers (FR-TOK-2 violated). The subject token is the service provider's own access token looked up in `identities`; the exchange requires its Rails session to be live (FR-TOK-7 met) and mints by `IdentityLinker#link_identity` against the target SP with `last_consented_at: now` (FR-CEN-12 violated: the target appears in connected services as if the user signed in there, and a later direct sign-in skips its consent screen). The minted token is a normal target access token that works at userinfo, so the service provider can read the target's attributes (FR-TOK-6 violated), and an `id_token` for the target is returned to the service provider. Lifetime is the service provider session's (FR-TOK-4 partial). Target revoked or in use by another live session is refused (FR-TOK-8 met). No volume monitoring or alerting (FR-TOK-20 as amended). Scope narrowing in claim space is careful but narrows attributes the service provider should never receive at all.

**Add.**
1. Client handling at the token endpoint by client type. A confidential client authenticates with `private_key_jwt` (`ResourceServerAuthenticator`, RFC 7523, RS256 pinned, `aud` must be the endpoint, five-minute lifetime, `jti` replay cache in Redis; also used by agencies at introspection and revocation). A public client sends `client_id` and a DPoP proof whose key thumbprint matches the binding of the subject token it presents, with `ath` over that token (RFC 9449 §4.3, §7); its own access token was bound at the code exchange, so a stolen subject token cannot be exchanged (FR-TOK-2, FR-TOK-19, FR-TOK-22; D19, D20).
2. `OpenidConnectTokenExchangeForm` (new body under the existing class name): dispatched from the existing token endpoint on `grant_type=urn:ietf:params:oauth:grant-type:token-exchange` (FR-TOK-1); subject token is the service provider's access token and its sign-in must be live for this first exchange (FR-TOK-7; D28); `resource` names exactly one registered API, so one token has one audience (RFC 8707, FR-TOK-3; D30); the grant for the application that owns that API must be live and current (FR-CEN-8; D1, D2); disabled scope, resource server, agency or service provider refuses (FR-CEN-16); IAL and AAL forwarded; the agency's allowed-service-provider list re-checked.
3. `TokenExchangeToken`: an opaque random reference, never a signed JWT (FR-TOK-21; D29). Storage is hybrid (D26): the live token is a Redis entry keyed by its SHA-256 digest, holding `aud`, `scope`, `delegation_id`, forwarded `ial`/`aal`, `refresh_family_id`, `dpop_jkt` and the issuance record id, with a TTL equal to the token's lifetime, and listed in a per-grant and a per-refresh-family index set so revocation can cascade (5.5); a secret-free issuance record (delegation id, grant, service provider, resource server, user, timestamps, token type, DPoP thumbprint, revocation) is a Postgres row for durability, billing, Attempts and the account page. Lifetime is 15 minutes by default; a resource server may configure a shorter maximum, never a longer one (FR-TOK-4, FR-TOK-5; D27). Not an `identities` row, so userinfo refuses it and nothing is created at the agency (FR-TOK-6, FR-CEN-10, FR-CEN-12, FR-TOK-8).
4. Response: `access_token`, `issued_token_type`, `token_type`, `expires_in`, `scope`, `refresh_token` (the refresh table arrives in 5.5; until then the response omits `refresh_token` and the family id is still recorded so 5.5 can attach to it). No `id_token`.
5. No hard rate limit on exchange: volumes and error rates per service provider are logged and monitored against configurable alert thresholds; runaway-caller protection is the infrastructure layer's (FR-TOK-20 as amended; D37).
6. Error mapping per RFC 8693 §2.2.2 (`invalid_request`, `invalid_target`, `invalid_grant`, `consent_required`), target-side errors withheld until the caller is authenticated. `consent_required` is returned, naming the `token_exchange:<value>` scope of the application that owns the resource, when the person has not approved that application or the approval lapsed, so the service provider can start a sign-in requesting it; it is given only to an authenticated caller for a registered resource. Every other resource problem is `invalid_target` (FR-TOK-26; D31).

**Remove, and why.**
1. `OpenidConnect::ExchangeController` and the `/api/openid_connect/exchange` routes: the exchange happens at the existing token endpoint (RFC 8693 §2.1), which already carries the CORS rule a browser-based public client needs; a second route and a second CORS entry add surface for nothing (FR-TOK-1).
2. Minting through `IdentityLinker` against the target and the `id_token` with `act` for the target: a delegated token must not be a sign-in credential at the agency, must not read attributes, and must not create a connection (FR-TOK-6, FR-CEN-12). The `act` fact moves to introspection and the SAML assertion (5.6, 5.9).
3. `IdTokenBuilder`'s `actor:` parameter and the `c_hash`/`nonce` omission: no `id_token` is issued for a delegation. Revert to `main`'s builder.
4. The `target_in_use` check: there is no target identity to hijack. The `target_revoked` idea survives as "a revoked service provider connection ends its grants" (5.3).
5. The claim-space narrowing (`BUNDLE_ATTRIBUTE_TO_CLAIM`, `target_scope`, `target_allowed_claims`): attributes are released only to the agency at introspection, bounded by the agency's own `attribute_bundle` (5.6).

### 5.5 Token lifecycle: refresh, revocation, suspension and deletion

**Worktree** `delegated-access-token-lifecycle`. **Depends on** 5.4, 5.10 (proof verification at refresh and revocation; D64).
**Requirements (as amended 2026-10-09):** FR-TOK-10, FR-TOK-11, FR-TOK-12, FR-TOK-13, FR-TOK-14, FR-TOK-15, FR-TOK-16, FR-TOK-18, FR-TOK-20 (refresh half), FR-CEN-13, FR-CEN-15 (suspension and deletion); companion §7 (REF-1..9 as amended in §5.5 and §7.6), §11. **Decisions:** section 9, D26, D32, D33, D37.

**What `sbx-taigrr` has.** Nothing: the minted token dies with the service provider's browser session (FR-TOK-15 violated), there is no renewal, no revocation endpoint, and revoking a grant does not stop an already-minted token (FR-TOK-10 to FR-TOK-16, FR-CEN-13 missing).

**Add.**
1. `TokenExchangeRefreshToken`: rotating, digest-only storage in Postgres (FR-TOK-18; D26), one family per exchange with an absolute 12-hour end counted from the first exchange for every approval, remembered or not, and never past `remember_until` (FR-TOK-10, FR-TOK-11; D32); reuse of a rotated token revokes the whole family, emits the Attempts event `delegated-access-revoked` with reason `refresh_token_reuse` (delivery is 5.7) and logs an analytics event (FR-TOK-12; D33); everything copied from the family so nothing can widen at renewal (FR-TOK-13).
2. `OpenidConnectRefreshTokenForm` at the token endpoint for delegated families (`grant_type=refresh_token`; client handling by client type as in 5.4: `private_key_jwt` for a confidential client, a DPoP proof from the family's key for a public client). No hard rate limit: refresh volumes and error rates per service provider are monitored against configurable alert thresholds (FR-TOK-20 as amended; D37).
3. RFC 7009 revocation endpoint `POST /api/openid_connect/revoke` (FR-TOK-14), authenticated the same way.
4. Grant revocation cascades to access and refresh tokens (FR-CEN-13): the live access tokens are removed from Redis through the per-grant and per-family index sets, and the issuance records and refresh tokens are marked revoked in Postgres (D26); account suspension and deletion revoke everything (FR-CEN-15); shorter family lifetime per service provider or per read-write API (FR-TOK-16) and a shorter access token maximum per resource server (D27) as configuration on the resource server and service provider.
5. Lifetime independent of the user's browser session (FR-TOK-15): already true of the token model in 5.4; the refresh family is what makes it useful.

**Remove, and why.** Nothing from `sbx-taigrr` remains in this area after 5.4.

**Amended 2026-10-09 (D59).** `POST /api/openid_connect/revoke` carries the same `Rack::Cors` treatment as the token endpoint (origins limited to registered redirect URIs, any request header, `POST` and `OPTIONS`), so the public-client service provider can revoke its families from the browser. Confidential clients and agencies are unaffected; `private_key_jwt` callers never preflight.

1. *Family absolute lifetime versus functional requirements section 6, question 2.* The 12-hour default is a configuration key; per-API shortening needs a column (`max_family_seconds` on the resource server) that `token-exchange2` does not have. Small addition. 2. *Revocation by assertion id for SAML* arrives with 5.9.

Checks in order, stopping at the first failure: `code_verifier` absent (`invalid_request`); the client (`invalid_client`); the shape, any `resource` refused outright (`invalid_request`, `resource_not_allowed_on_refresh`: the audience is the family's, a service provider wanting another API exchanges again) and `refresh_token` present without null bytes (`invalid_request`); the public client's proof for POST to the token URL with no `ath`, since no access token is presented, verified before the token is looked up so a caller without a valid proof learns nothing about it (`invalid_dpop_proof`); the token, found and this client's, or `invalid_grant` with one wording (`invalid_refresh_token`); for a public client the proof thumbprint equal to the family's `dpop_jkt` (`invalid_dpop_proof`, `dpop_key_mismatch`); `scope`, if given, exactly the family's (`invalid_scope`).
6. *Rotation.* `#rotate_and_mint!` re-reads the row under `SELECT … FOR UPDATE` (`TokenExchangeRefreshToken.lock.find`) so of two concurrent refreshes the second waits and then sees the row spent. An unspent row is refused `invalid_grant` if revoked or past the family end; if the approval no longer stands (`approval_stands?`: not revoked, `current_content?`, a remembered approval still within `remember_until`; a single-authorization approval stands for as long as its family) the family is revoked with reason `approval_lapsed` and the refresh refused; if the API is not `usable?` or the application no longer `accepts_delegation_from?` the client, the refresh is refused and nothing is revoked, so switching the record back on restores the family. Otherwise `used_at` and `rotated_at` are set and `#mint!` writes the next issuance record (same grant, resource server, service provider, user, delegation id, scope, family id and `dpop_jkt`; `ial`, `aal` and `sp_rails_session_id` from the previous record; `token_type` from the binding) and the next refresh row (same family id, same `expires_at`); after commit `DelegatedTokenStore.write` adds the live entry to the family's index set with TTL the lifetime. The response has the exchange's shape.
7. *Reuse.* A spent row presented again has `used_at` updated and, unless the family is already revoked, `TokenExchangeRefreshToken.revoke_family!(family_id, reason: 'refresh_token_reuse')` runs (`DelegatedTokenStore.revoke_family` deletes the family's live entries and set; the family's refresh rows and issuance records are marked, rows already revoked keeping their reason), `reuse_detected?` is true and the Attempts seam `report_family_revoked(reason:)` is called (an empty method; delivery is 5.7), so one theft is reported once. The answer is `invalid_grant` (`refresh_token_reused`) telling the service provider to exchange again.
8. *Analytics.* `openid_connect_token_refresh(success, service_provider_issuer, resource_server_identifier, application_issuer, client_type, token_type, family_id, reuse_detected, expires_in, error_code, error_details)`; the controller also logs `delegation_refresh_token_reuse(service_provider_issuer, resource_server_identifier, family_id)` when `reuse_detected`, an event operations can alert on; `sp_integration_errors_present` is fed with `event: :oidc_token_refresh_request`. Nothing refuses for volume (D37).
9. *Revocation endpoint.* `POST /api/openid_connect/revoke` and its OPTIONS route; `OpenidConnect::RevokeController` (no session, no CSRF, 404 through `RenderConditionConcern` while `token_exchange_enabled` is off, proof read from the `DPoP` header only) and `OpenidConnectRevokeForm`: the client (`invalid_client`, 401), `token` present (`invalid_request`, 400), the public client's proof for POST to the revoke URL with `ath` over the token (`invalid_dpop_proof`, 400). `token_type_hint` only orders the two lookups. For each recipient of an approved application that is `attempts_api_deliverable?` it creates the person's `AgencyIdentity` at that agency if missing (`AgencyIdentityLinker.for(..., skip_create: false)`, never an `identities` row), forwards the buffered events re-mapped once per recipient per session (`buffer_delivered_to`), writes one `delegated-access-consented` event per approval through `DelegatedAccessEvents.consented`, releases the stored `idv-*` history under the once-per-recipient rule and, only when the current sign-in is to the service provider the approvals are for, marks the recipient approved in the context so later session events reach it live (D66). Nothing names an application the person did not approve, so a declined agency receives nothing and gets no identifier (FR-FRD-3). A release is marked against the SP request id (`mark_released`) and the handoff checks `released_for?`, so one authorization is released once whether the screen was shown or skipped (ATT-13; D67). Delivery never blocks the person: a failing recipient is reported to error tracking and logged, and the others continue.
5. *Historical release.* `AttemptsApi::HistoricalReleaseCheck` (the profile has a `UserProofingEvent`, not already sent to this recipient, an encrypted file reference exists) is extracted from `Idv::HistoricalAttemptsConcern#send_historic_events?`, which keeps its `idv_requested?` test and calls the shared check, so the direct path and the delegated path cannot drift. The delegated release requires `historical_attempts_api_enabled` and a verified person, not that the service provider's request be an identity-verification request (ATT-15); when `Cacher#fetch` is empty (remember-device or PIV/CAC sign-in) nothing is released and the once-only flag stays unset. `Tracker.write_existing_user_events` and `HistoricalAttemptEvent` take `extra_metadata:`, so released `idv-*` copies carry `delegation_id` and `actor_issuer` (ATT-14).
6. *Live fan-out.* After approval, `Tracker#capture_for_delegation` also writes each later event of the browser session (login completed, re-authentication, MFA changes, logout, timeout, rate limits) to every approved recipient at once through `AttemptsApi::DelegatedEventWriter#forward`, re-mapped with the identifier and delegation id resolved once at release (FR-FRD-4, ATT-8). A recipient that is no longer enrolled, or a copy that cannot be written, never affects the service provider's own event.
7. *Writer.* `AttemptsApi::DelegatedEventWriter` has two paths. A forwarded copy keeps the event type, `jti`, timestamps, `subject.session_id` (still the service provider's value, ATT-3), IP address, user agent, device id, `application_url` and every event-specific field, replaces `user_uuid` with the person's identifier at the agency, drops `google_analytics_cookies` and adds `delegation_id` and `actor_issuer`. A written server-side event (consent, token, revocation) has `subject.session_id` null and carries `user_uuid`, `delegation_id`, `actor_issuer`, `application_url: nil`, `language` and `aws_region`, and no IP address, user agent, port or device (functional requirements section 8, question 5: no network information). Both encrypt to `recipient.attempts_public_key` and store under the recipient's issuer with `AttemptsApi::RedisClient#write_event`, as `Tracker#track_event` does, so the agency polls them through the existing endpoint with the existing acknowledge-to-drain contract (ATT-18). Every outcome is logged as `delegated_access_attempts_delivery(event_type, recipient_issuer, actor_issuer, success, event_count, skipped_reason, exception)`; `skipped_reason` is `delivery_disabled` or `recipient_not_enrolled`.
8. *Token and revocation events.* `DelegatedAccessEvents.token_issued` is called from `OpenidConnectTokenExchangeForm#issue!` after the live entry is written and `DelegatedAccessEvents.access_revoked` from `TokenExchangeGrant#revoke!` after the tokens are ended; `.token_refreshed` and the reuse call (`access_revoked(reason: 'refresh_token_reuse', resource_server:)`, to the one API whose family ended) are wired through the refresh form's mint path and its `report_family_revoked` seam once the lifecycle branch sits below this one in the stack. `delegated-access-token-issued` and `delegated-access-token-refreshed` carry `application`, `resource`, `scope`, `ial`, `aal`, `token_type` (`Bearer`, `DPoP` or `N_A`), `token_format` (`oauth` or `saml2`) and `expires_at`, never the token or anything derived from it; `delegated-access-revoked` carries `application`, `resource` (null when the whole approval ended) and `reason` (`user_revoked`, `sp_disconnected`, `refresh_token_reuse`, `account_suspended`, `account_deleted`, `client_revoked`); `superseded_by_new_consent` is never reported, since the re-approval carries the live tokens over (E97) and nothing ended for the agency. `delegated-access-consented` carries `application`, `scope`, `remembered`, `source` (`consent_screen` or `account_page`) and `consented_at` (epoch seconds; the original consent time on a reuse). Every server-side event is attributed to the person's `AgencyIdentity` uuid at the recipient's agency and carries `unique_session_id` as the SHA-1 hex digest of the person's `unique_session_id`, the same hash the sign-in's events carry, so the agency can join a token to its sign-in without learning the session identifier. `delegation_id` is the earliest approved grant's for that recipient, the value introspection returns (ATT-14). The event names differ from the plan's shorthand (`delegation-consented`, `delegated-token-issued`): every delegated event is prefixed `delegated-access-`.

### 5.10 Client key binding (DPoP) for the public client

**Worktree** `delegated-access-dpop`. **Depends on** 5.1, 5.2, 5.3 and 5.16 (site-keys) only. In the stack it sits right after `delegated-access-site-keys` and before `delegated-access-token-exchange`, so every delegation branch above it calls the verifier instead of carrying a piece of it (D64).

### 5.14 Encrypted userinfo responses (planned)

**Decision** D50 (section 9). **Depends on** 5.1 (certificates on the service provider record), 5.12. **No code is written this phase.**

The whole userinfo attribute bundle is returned as a JWE (RFC 7516) encrypted to the client certificate registered for the service provider that the presented access token belongs to, following OpenID Connect Core 5.3.2 (`userinfo_encrypted_response_alg` and `userinfo_encrypted_response_enc` as client metadata). The key-selection rule is the point of the design: `AccessTokenVerifier` resolves the token to its `identities` row and its service provider, and the response is encrypted to that service provider's registered certificate, never to a key named in the request. A service provider without a registered encryption certificate, or without the metadata, receives the plain JSON response as today. It applies first to the Department of State's attributes (the selfie and document data of 5.12), so that the edge, logs and any intermediary see ciphertext (the end-to-end property FR-DOS-12 asks for), and would then be available to any service provider that opts in. Delegated tokens remain refused at userinfo regardless (FR-TOK-6), so this changes nothing for agencies reached by delegation.

### 5.16 Per-site keys: sealing primitives and custody (ported)

**Worktree** `delegated-access-site-keys`. **Depends on** nothing in the delegation chain: the feature is independent of 5.1 to 5.15. It was first placed at the top of the stack; since 2026-10-10 it sits after `delegated-access-account-page` and before `delegated-access-dpop` (D64), so every delegation branch from 5.4 on builds on it. **Source:** pull requests #13618 (*Add sealing primitives for per-site keys*) and #13619 (*Store per-site key roots wrapped under the user's password*) of the per-site-keys series on `18F/identity-idp`, cherry-picked as two commits. #13617 (a CSP fix) is already in the base through `main`. #13620 (release of the sealed key on OIDC authorization), #13621 (recovery after password reset) and #13622 (recovery with the personal key) are not ported and are listed below as follow-ups. **Requirements:** functional requirements section 12 (FR-KEY-1 to FR-KEY-7); companion §17, Appendix E row E92. **Decisions:** section 9, D56.

**What it adds.** A per-site key is a key unique to a user and a service provider, the same on every device the person uses, and delivered only to the service provider's browser. This phase ports the building blocks and the custody of the per-user root. Nothing releases a site key yet.

1. *Sealing primitives (#13618).* `SiteKeys::RecipientJwk` parses the `site_key_jwk` a relying party's browser will send: base64url JSON of a P-256 public JWK. The WebCrypto `exportKey('jwk')` metadata members (`ext`, `key_ops`, `alg`, `kid`, `use`) are accepted and ignored; any other member, including a private `d`, is rejected, as are off-curve points and coordinates that are not 32 bytes. `SiteKeys::Sealer` encrypts a key to that JWK with ECDH-ES, HKDF-SHA256 and AES-256-GCM; the HKDF info and the GCM additional authenticated data are both `"login.gov site key wrap v1\n<client_id>"`, so a sealed key is bound to one service provider; the output is base64url JSON `{v, epk, iv, ct}`. `Encryption::AesCipher` and `Encryption::AesCipherV2` raise a typed `Encryption::DecipherError` when a payload fails authentication, so a caller can tell a wrong key from any other failure.
2. *Custody (#13619).* A `site_key_roots` table holds 32 random bytes per user, wrapped with `Encryption::Encryptors::PiiEncryptor` (scrypt of the password plus KMS), the scheme profile PII already uses, so Login.gov cannot unwrap a root without the password. `SiteKeys::Vault` unwraps the root when the password is entered and keeps it KMS-encrypted in the session together with a fingerprint of the stored wrap, so a session re-locks when another session changes the wrap. A root is created only when the person signs in to a service provider whose record has the new `site_key_allowed` column; the column is settable only from `service_providers.yml`, and `ServiceProviderUpdater` ignores it, so the Dashboard cannot turn it on. Sign-in unwraps the root before the second factor; a wrap that fails under a just-verified password is replaced at the next password prompt after the second factor unless a concurrent password change explains the failure. A password change re-wraps the root in the same transaction under a row lock; when the root is locked in the session, the password page asks for the current password first; a root that cannot be re-wrapped is deleted. Every password reset path (forgot password, reset from a disavowal link, `ResetUserPassword`) deletes the root, and the foreign key cascades on user deletion. Two analytics events (`site_key_root_created`, `site_key_root_unlock_failed`) record custody changes without the key material. All of it is behind `site_key_enabled`, default `false`.

**Port details.** Two "both added" conflicts were resolved by keeping both sides: `app/models/service_provider.rb` (the delegation columns and `site_key_allowed`), its spec, and `db/schema.rb`. The ported migrations `20261003110000_create_site_key_roots` and `20261003110001_add_site_key_allowed_to_service_providers` predate the delegation migrations (`20261009…`) in timestamp order, so a fresh database applies them first and the schema dump needs no reordering. Verified locally: 282 examples across the touched specs pass; rubocop and the analytics-events lint are clean.

**Known limitation (from the source).** A transient unlock failure followed by a password change deletes the root; the series later changes this to dropping only the password wrap (#13621, #13622, not ported).

**Follow-ups, not in this phase.** Release of the sealed key on OIDC authorization (#13620); recovery of the root after a password reset (#13621) and with the personal key (#13622).

**Relation to delegated access.** Independent code paths: nothing in 5.1 to 5.15 reads a site key root, and nothing here reads a grant, a token or a resource server. The sealed key is delivered only to the service provider's browser, which fits the public-client baseline of section 9 (D19): the service provider's page holds the site key as it holds its DPoP key, and no server of the service provider sees either. There is no interaction with grants or tokens in this phase; whether a released site key should ever be tied to a delegation is a question for the follow-up pull requests, not for this one.

## 6. Cross-cutting considerations

1. **Order of operations is forced by the schema.** 5.1 is the only step everything waits on. 5.2 and 5.3 (consent and account) are independent of 5.4 (exchange) once the grants table exists; 5.5, 5.6, 5.7, 5.8 all need 5.4; 5.9 and 5.10 need 5.6. This is the same chain as companion Appendix D.3, with the `sbx-taigrr` removals attached to the feature whose premise they contradict. **Amended 2026-10-10 (D64).** 5.10 depends only on 5.1 to 5.3 and 5.16 and precedes 5.4 in the stack; 5.4, 5.5 and 5.6 depend on it.
2. **Migrations replace; nothing is kept for compatibility.** The sandbox database has `sbx-taigrr`'s schema, so every structural change is a new migration file that drops what changes shape and creates what replaces it. No table, column, class or method is kept under a `legacy`, `old` or similar name because it might be in production: neither branch is. `allow_unsafe_migrations` is already true for the `agroot` environment.
3. **Two things named the same.** Section 3.3 lists the collisions. Each is resolved inside the feature that owns the new meaning; no shim keeps both meanings alive, because a dual meaning in `token_exchange_grants` or `OpenidConnectTokenExchangeForm` would be worse than a clean replacement.
4. **The reviewer's billing note changes an accepted design.** BIL-13 in the requirements document and *How billing works under delegated access* describe the mutation-based waiver. Once 5.8's decision 1 is taken, both documents and FR-BIL-8's "together with the first agency charge" need a one-paragraph update describing the adjustment row instead. Taken 2026-10-09 (D40–D43): the companion's §9.5 and FR-BIL-1 and FR-BIL-8 carry the update.
5. **Specs.** `sbx-taigrr` adds 206 examples, `token-exchange2` 326. Specs for removed `sbx-taigrr` behavior are deleted with the behavior; ported specs come with their code. The live harness in `identity-sts-sinatra` is the acceptance test for 5.4 onward and needs the fixtures from 5.1 and 5.11.

### 6.2 Productionizing the registry: the Dashboard

A survey of `identity-dashboard` on 2026-10-10, made before D77 was taken, of what it would take for partners to maintain the delegated-access content there.

1. *Nothing exists yet.* The Dashboard has none of the delegation fields: no agency or application consent content, no `token_exchange_enabled_sp`, no `delegation_*` columns, no resource servers, no content versions.
2. *One payload to extend.* A single `ServiceProviderSerializer` feeds both the push to the identity provider and the pull API, so the nested `token_exchange_resource_servers` payload with the new columns is one file to extend, and identity-idp's `ServiceProviderUpdater` already consumes that shape (5.1 item 6).

4. *New work.* Nested child rows for resource servers under an application (the Dashboard has no has-many-through-the-form pattern); the production wizard as a second edit path that must carry the same fields; agency editing, for which no CRUD surface exists at all; the content-version user experience (an editorial bump on every save, a material bump only when the editor says so, D9); and validations that live in the shared `IdentityValidations` gem, which both repositories load.
5. *Two product decisions gate it.* Who marks a change material (the partner editing, or Login.gov reviewing), and whether the fields are admin-only or partner self-service with Login.gov approval (FR-ONB-5).

### 7.3 Two routes to a sandbox

**Route A: a Chef-managed personal environment (the `agroot` model).** Full fidelity: EC2 hosts, workers, Redis, S3, the Attempts API's S3 storage, scheduled reports, real `identity-idp-config` and Dashboard. **Route B: a GitLab review app.** Any non-`main` branch pipeline on `lg/identity-idp` runs `build-idp-image` and the `review-app` job, which applies an ArgoCD `Application` from `identity-eks-control` (`cluster-reviewapp/envs/reviewapps`) and brings up `https://<slug>.reviewapps.identitysandbox.gov` with its own PostgreSQL, Redis, PIV/CAC and a Dashboard at `<slug>-portal`, stopping after two days. ### 7.4 What to do differently so the branch runs in a sandbox

1. **Keep `main` close.** Section 2's merge, repeated whenever `main` moves materially, so a sandbox deploy of the branch is a deploy of current Login.gov plus the feature.
2. **Every new config key has a safe default in `application.yml.default`** (all of `token-exchange2`'s do) so the branch boots in any environment with no `application.yml` change, and the feature is off until the environment's file turns it on. For the sandbox, the `application.yml` change is one block: `token_exchange_enabled: true`, the TTLs and rate limits, `delegation_outcomes_report_emails`, `attempts_api_enabled: true` with the agency issuers in `allowed_attempts_providers` and their keys, and for the review app the same block in `identity-eks-control` by merge request (it affects every review app, which is harmless because the feature is still gated by service provider records).
3. **A sandbox seeding path that does not touch `identity-idp-config`.** Because the shared config repo cannot carry keys that `main` does not know, and the Dashboard has no fields, the branch needs its own way to load the fictitious service provider, the agency SPs, their resource servers, scopes and certificates in a sandbox: a rake task (`delegated_access:seed_sandbox`) that reads the same `config/delegated_access.localdev.yml` the local seed task and the end-to-end harness use (D51; fictitious agency names, hostnames substituted from the environment) and refuses to run when `Identity::Hostdata.env` is `prod` or `staging`. `token-exchange2`'s seeder already accepts nested resource servers and inline PEM certificates (`TokenExchangeResourceServer#load_cert` reads a PEM string from the `certs` column), so no `certs/sp` file and no `identity-idp-config` change is needed. 4. **Resource server certificates in the database, not on disk.** Follows from 3; the reference agency applications already generate their key pairs with `make rs_keypair`, and the public certificate is pasted into the seed file for the environment.
5. **Reference applications stay where they are.** Nothing in the design has the IdP call an agency or the service provider; agencies call introspection and poll the Attempts API; the service provider calls the token endpoint; the browser does the rest. The three Sinatra applications can therefore run on a developer machine against a sandbox IdP with `localhost` redirect URIs (as `identity-oidc-sinatra` does against `int` today), and the harness runs the same way with `IDP_URL`, the test user and the Attempts poll tokens pointed at the sandbox. 8. **Workers and reports.** The outcomes report registers in `job_configurations.rb` like every other report and writes to the reports bucket behind `s3_reports_enabled`; on Route B there are no workers, so 5.8's reports are verified on Route A or by running the job from the console.

The WAF rules in `identity-devops/terraform/waf` should be checked once for path allow-lists before the first agency call; the token endpoint's existing rules are the model.
10. **No CORS, no browser endpoint.** Removing `sbx-taigrr`'s `/exchange` CORS rule (5.4) also removes the only infrastructure-visible difference between this branch and `main`'s HTTP surface, apart from the two new paths above. **Amended 2026-10-09 (D59).** The two new paths carry the token endpoint's CORS treatment so a browser public client can reach them; the WAF check in item 9 should include the `OPTIONS` preflight on all three.
11. **Schema in the sandbox.** Route A's `agroot` database already has `sbx-taigrr`'s tables; 5.1's drop-and-create migration is what makes a redeploy of the new branch onto it succeed. Route B starts from an empty database every time, so both migration paths get exercised.
12. **Deploy from GitHub.** Until the branch is on GitHub, Route A is closed. The GitLab mirror overwrites diverged branches, so once `login-delegated-access` exists on GitHub, GitHub must be where it is pushed from then on (or the mirror will revert GitLab-only commits). Decide the home of the branch before the first push to GitHub.

### 2026-10-09 interview, feature 5.1 (onboarding data model and configuration)

Decisions taken with the product owner, applied to this document, the functional requirements (amended rows and Appendix D) and the requirements document (§3.4, §4.8, Appendix E rows E37–E45).

1. **D1 — Application = agency SP record; consent per application.** An application is one agency-owned `service_providers` row with consent content, owning one or more resource servers (URLs). A person can approve one application at an agency and not another. Rationale: people think in applications, not agencies. Changes FR-CUX-3 and companion CON-7/CON-10 from agency-level to application-level.
2. **D2 — One scope per application.** The service provider requests `token_exchange:<application scope value>`; the application's URLs are listed for information; `resource` selects one at exchange. The `token_exchange_scopes` table is not built. Rationale: fewer boxes, matches how partners describe an integration.
3. **D3 — Content is edited in the Dashboard.** Agency and application consent content (and service provider content) are Dashboard fields synced by `ServiceProviderUpdater`; production via the seeder. The Dashboard change is a separate repository and an explicit dependency, called out in code comments and in the requirements documents. Until it lands, D10 applies.
4. **D4 — Account-page pre-approval is consent.** The account page lists every registered application that accepts the service provider, grouped by agency; turning one on creates a remembered grant for up to 12 months from that moment; the consent screen honors it.
5. **D5 — Requested applications are take-it-or-cancel.** Applications named in the request appear selected and locked; declining one means cancelling the sign-in, as for requested attributes today. Reverses FR-CUX-4/5 and FR-CEN-6; per-application declines are no longer recorded because none exist.
6. **D6 — The remember choice stays for requested applications.** "Remember my approvals for 12 months", unchecked by default; unchecked means this sign-in only. Account-page pre-approvals are always remembered. FR-CUX-7 and FR-CEN-11 stand.
7. **D7 — Opt-in and approval live on SP records.** `allowed_delegation_service_providers` on the application (empty means any approved service provider); `token_exchange_enabled_sp` on the service provider. The `token_exchange_service_providers` config key is removed; `token_exchange_enabled` remains the master switch.
8. **D8 — Grant key is (user, service provider, application).** One live row, with source, consent time, remember-until, content versions, delegation id, revocation. Not keyed to the service provider identity's session, because pre-approval happens outside any sign-in.
9. **D9 — Only material content changes re-ask.** Every content edit bumps a version; the editor marks it material or not; a material change invalidates remembered grants for that application (or for everything under that agency or service provider). Narrows FR-CEN-5 and CON-12.
10. **D10 — Branch seed file and env-guarded rake task** for local, review-app and sandbox data until the Dashboard fields exist; the dependency is stated explicitly in comments and documents.
11. **D11 — Full terminology sweep in 5.1.** Every "broker" identifier, string and comment, and every public-client or browser-callable comment, is corrected in 5.1 even in code later features delete.
12. **D12 — Agency-level content lives on `agencies`.** Localized description and learn-more URL alongside the existing name and logo, editable on the Dashboard's agency record.

**Effect on later features.** Sections 5.4 to 5.11 still describe scopes per API in places (for example "a grant for that API" in 5.4 and `scope` handling in 5.6). Each is reconciled with D1/D2 at that feature's own interview before implementation; the exchange still issues a token for exactly one resource server URL of an approved application.

### 2026-10-09 interview, features 5.4 to 5.7 (token exchange, lifecycle, introspection, fraud signals)

Decisions taken with the product owner, applied to sections 5.4 to 5.7, the functional requirements (amended rows, FR-TOK-26 and Appendix D) and the requirements document (§5.2, §5.6, §6.3, §6.4, §7.5, §7.6, §8.3, §10, §11, Appendix E rows E62–E75).

26. **D26 — Token storage is hybrid.** Delegated access tokens and SAML assertions are stored in Redis keyed by their digest with a TTL equal to their lifetime, plus per-grant and per-refresh-family index sets so revocation can cascade; refresh tokens (rotating, digest-only) and a secret-free issuance record (delegation id, grant, service provider, resource server, timestamps, token type, DPoP thumbprint, revocation) live in Postgres for durability, billing, Attempts and the account page. Rationale: short-lived tokens expire themselves and introspection is a hot lookup; refresh families (up to 12 hours, rotation, reuse detection) and reporting need durability. Rejected: Postgres-only (table growth, purge jobs) and Redis-only (loses refresh durability and issuance history). The companion's `token_exchange_tokens` table is read as the issuance record (§5.2 as amended). (FR-TOK-18, FR-VER-1.)
27. **D27 — Delegated access token lifetime is 15 minutes by default;** a resource server may configure a shorter maximum (for example a read-write API), never a longer one. (FR-TOK-4.)
28. **D28 — The service provider's Login.gov sign-in must be live for the first exchange.** Afterwards the refresh family carries access independent of the browser session. (FR-TOK-7 confirmed, FR-TOK-15.)
29. **D29 — Delegated tokens are opaque references** (random string, stored hashed); agencies learn everything through introspection. Rejected: signed JWTs, whose claims are visible to the service provider and which still need introspection for revocation. (FR-TOK-21.)
30. **D30 — Exactly one `resource` per exchange;** one token has one audience. (FR-TOK-3.)
31. **D31 — Refusals for a missing or lapsed approval are `consent_required`,** naming the `token_exchange:<value>` scope so the service provider can start a sign-in requesting it; given only after the caller is authenticated and the resource is registered. Every other resource problem is `invalid_target`. (FR-CEN-8, FR-TOK-26.)
32. **D32 — The refresh family's absolute lifetime is 12 hours from the first exchange** for every approval, remembered or not, never past the approval's `remember_until`. Rejected: ending the family with the Login.gov session for non-remembered approvals; a 4-hour default. (FR-TOK-10, FR-TOK-11.)
33. **D33 — Refresh token reuse revokes the whole family,** emits the Attempts event `delegated-access-revoked` with reason `refresh_token_reuse` and logs an analytics event (RFC 9700 §4.14.2). (FR-TOK-12.)
34. **D34 — Introspection releases attributes by session state.** While the person's Login.gov sign-in is live, the attributes the agency's registered attribute bundle allows, in userinfo shape; after the session ends, only `sub`, `delegation_id` and email, with the response stating that. (FR-VER-4, FR-VER-5 confirmed.)
35. **D35 — The agency's `sub` is the agency-level pairwise identifier** (the existing `AgencyIdentity` uuid), created if the person has never used that agency; no `identities` row is created. (FR-VER-3, FR-CEN-12.)
36. **D36 — Who may introspect.** The resource server named in `aud` (`private_key_jwt`) gets the full active response. The public-client service provider may also introspect its own delegated tokens, but only with a DPoP proof bound to the token (`ath`) and to the key the token is bound to; it receives the token status (`active`, `exp`, `iat`, `aud`, `scope`, `delegation_id`, `token_type`, `cnf`) plus the claims the `openid` scope conveys about the person (its own pairwise `sub`, `iss`) and any further attribute an agency explicitly marks as shareable with the service provider, and no other identity attribute. Any other caller gets `{"active": false}` with no reason (RFC 7662 §2.2). (FR-VER-2, FR-VER-6.)
37. **D37 — No hard rate limits and no cache guidance.** Exchange, refresh and introspection have no per-caller ceiling (no 429) for registered callers: nationwide use with several agencies per person in quick succession makes per-caller ceilings harmful. Volumes and error rates are monitored against configurable alert thresholds; runaway-caller protection is left to the infrastructure layer. Agencies introspect on every call, so revocation is seen immediately. Supersedes the 60-second cache window and the per-caller rate limits formerly in 5.4, 5.5 and 5.6. (FR-TOK-20, FR-VER-7, FR-VER-8.)
38. **D38 — The fraud-signal plan stands in full:** buffer the sign-in session's Attempts events while a delegation request is in flight; at consent release them to each approved agency under its pairwise identifier with a `delegation-consented` event and the identity-verification history (once per agency); forward later session events while the sign-in is live; emit token issued, refreshed and revoked events with `delegation_id`. Delivery stays behind the master switch pending privacy review. (FR-FRD-1 to FR-FRD-9.)
39. **D39 — A remembered approval reused on a later sign-in** sends the agency that sign-in's events and a consent event marked remembered, every time. (FR-FRD-7 confirmed.)

### 2026-10-09 baseline change: the service provider is a public client

Raised by the product owner after 5.1 landed; replaces the confidential-client baseline of the morning. Decisions 19 to 22, confirmed by the product owner the same day.

19. **D19 — Public client with DPoP.** The service provider is a browser-based public client (PKCE, no `private_key_jwt`). Every token it holds is bound to a key it holds with DPoP: its own access token, the delegated tokens, and the refresh tokens. Login.gov verifies the proof at the code exchange, the token exchange, refresh and userinfo; agencies verify it on API calls using `cnf.jkt` from introspection. Confidential clients keep `private_key_jwt` and bearer tokens unchanged. Delegated tokens remain refused at userinfo, so an agency's attributes are reachable only through introspection, which the agency authenticates to.
20. **D20 — DPoP is mandatory for every public client approved for delegation** (a property of the service provider record, not a per-request option): the code exchange, the token exchange, refresh and userinfo all require a proof for such a client. Confirmed.
21. **D21 — The authorization code is bound to the key too**, through the `dpop_jkt` authorize parameter (RFC 9449 §10), so an intercepted code cannot be redeemed with another key. Confirmed.
22. **D22 — Server nonces (RFC 9449 §8) stay deferred** (E28), with the rationale below recorded for the risk-based decision. Confirmed.

**Rationale for deferring server nonces (D22), for the risk-based decision.** The threat a nonce addresses is a proof that is created ahead of time or captured and replayed within its validity window. The controls already in place bound that window tightly: a proof is accepted only if its `iat` is within 60 seconds past or 10 seconds future, its `jti` has not been seen at Login.gov in that window (single-use, kept in Redis), its `htm` and `htu` match the request, and its `ath` matches the token it accompanies; agencies apply the same checks on API calls. A captured proof is therefore usable only for the same method and URL, with the same token, within a minute, and only once at Login.gov. What remains is a proof pre-computed by code running in the service provider's page for a future request to a known URL; a server nonce would force that code to fetch a fresh nonce first, which it could also do if it controls the page, so the nonce raises the bar without closing the case. Against that, a nonce costs an extra round trip on every first request (`use_dpop_nonce`), nonce state and rotation at Login.gov and at every agency, and a second failure mode for partners to handle. Decision: defer; keep the 60-second window and single-use `jti`. Revisit if a partner's clock skew makes the window too tight, if a deployment shows pre-computed proofs in the wild, or if an agency asks for nonces on its API.
