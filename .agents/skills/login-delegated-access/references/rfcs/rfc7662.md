# RFC 7662 — OAuth 2.0 Token Introspection

RFC 7662 defines the endpoint a protected resource calls to learn whether a token is active and
what it stands for. Because delegated tokens here are opaque (D29), introspection is the only way
an agency API learns a token's audience, scope, the person and the acting service provider. The
public-client service provider may also introspect its own token, with a DPoP proof, to tell an
expired token from a failing API. Canonical text: https://www.rfc-editor.org/rfc/rfc7662.txt

## Sections this implementation relies on

- **§2.1 Introspection request.** `POST` with `token` REQUIRED and `token_type_hint` OPTIONAL; the
  endpoint MUST require some form of authorization so it cannot be used to scan for valid tokens.
  `OpenidConnectIntrospectForm#identify_caller` (`app/forms/openid_connect_introspect_form.rb`)
  authenticates an agency API by `private_key_jwt` (`ResourceServerAuthenticator`,
  `key_source: :resource_server`, `aud` the introspect URL) or a public service provider by
  `client_id` plus a DPoP proof with `ath` over `token` (`#verify_service_provider_proof`).
  Companion INT-1 as amended; D36, D62. `token_type_hint` is accepted and not needed: the store is one lookup by digest.
- **§2.2 Introspection response.** `active` REQUIRED; `scope`, `client_id`, `token_type`, `exp`,
  `iat`, `sub`, `aud`, `iss`, `jti` OPTIONAL; implementations MAY add top-level members. For an
  inactive token, or a caller not permitted to introspect it, the response is `active: false` and
  SHOULD NOT say why. `#token_members` returns the standard members plus `delegation_id` and `cnf`;
  `#resource_server_response` adds `sub`, `act` (RFC 8693 §4.1), `jti`, `acr`, `aal`, `auth_time`,
  `session_live` and the identity claims from `DelegatedTokenClaims#agency_claims`
  (`app/services/delegated_token_claims.rb`); `#response` returns exactly `{active: false}`
  otherwise (INT-2, INT-3, INT-4, INT-10, INT-14; D34, D35, D63).
- **§2.3 Error response.** If the caller's client credentials are invalid, HTTP 401. `#http_status`
  is 401 for a failed credential; `#www_authenticate` adds the RFC 9449 §7.1 `DPoP` challenge when
  the public client's proof fails (INT-1 as amended 2026-10-10).
- **§4 Security considerations.** The server MUST verify that the caller is allowed to introspect
  the token (typically the token's audience), MUST NOT leak information about inactive tokens, and
  callers MUST authenticate. `#caller_entitled?` admits the token's resource server, or the holder
  whose verified proof key equals the token's `dpop_jkt`; a wrong-key proof is "not active", not an
  error (D62). `#token_active?` folds expiry, revocation, suspension, approval state and kill
  switches into one "not active".

## Deliberate choices and deviations

- **Two kinds of caller, two responses.** The agency receives the full response including the
  person's identity claims in userinfo shape; the service provider receives a limited one
  (status, `aud`, `scope`, `delegation_id`, `token_type`, `cnf`, its own `sub`, and any attribute
  the application chose to share). Rationale: companion §6.4 "Why INT-1/INT-14", D36.
- **Identity claims as extension members** (INT-10, "Why INT-10"): the agency behaves as after a
  direct sign-in; `userinfo` is never usable with a delegated token.
- **`jti` is the token's hex SHA-256 digest** (D63, E101), the key the live entry is stored under.
- **No credential is `{active: false}`, not 401** (D62): a request with neither a client assertion
  nor a public `client_id` is answered without examining the token.
- **No cache window and no rate limit** (D37): agencies introspect on every request, so revocation is
  seen at the next request.
- **Token format is unrestricted** (§2.1 does not restrict it): a SAML assertion is introspected by
  its `ID` or by the encoded plaintext assertion (`DelegatedSamlAssertion.reference_for`); an
  encrypted assertion hides its ID and is "not active".
- **Validity is a Redis read** (`DelegatedTokenStore.read`, `app/services/delegated_token_store.rb`);
  the issuance record is never consulted (INT-15, D26).

## Questions this digest answers

- Who may introspect a token? Its audience (the agency API), or the public client that holds it and proves its key.
- What does a wrong caller get? Exactly `{"active": false}`, HTTP 200.
- When is the answer 401? When a presented credential fails: `invalid_client` for an assertion, `invalid_dpop_proof` with `WWW-Authenticate: DPoP` for a proof.
- Is `act` always present for the agency? Yes; Login.gov introspects only delegated tokens (INT-4).
- What does `session_live` mean? Whether the person's decrypted profile is still available; `false` means identifiers and email only (D34).
- How is `sub` computed? The agency-level pairwise identifier (`DelegatedTokenClaims#agency_sub`), never an `identities` row.
- May the agency cache `active: true`? No guidance is published; introspect every request (D37).
