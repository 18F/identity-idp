# RFC 7638 — JSON Web Key (JWK) Thumbprint

RFC 7638 defines a stable, canonical hash of a public key: the JWK Thumbprint. In this repository
the SHA-256 thumbprint of a client's DPoP key is the key's identity everywhere: it is sent as
`dpop_jkt` on the authorization request, stored on `identities.dpop_jkt` and
`token_exchange_tokens.dpop_jkt`, compared against each later proof, returned by introspection as
`cnf.jkt` (RFC 7800, RFC 9449 §6) and carried in a SAML assertion as the `dpop_jkt` attribute.
Canonical text: https://www.rfc-editor.org/rfc/rfc7638.txt

## Sections this implementation relies on

- **§3 JWK Thumbprint.** Build a JSON object containing only the required members of the key's
  type, with member names in lexicographic order and no whitespace; hash the UTF-8 bytes; base64url
  encode the digest. `DpopProofVerifier.thumbprint` (`app/services/dpop_proof_verifier.rb`)
  computes it with `JWT::JWK::Thumbprint`, which implements this construction with SHA-256.
- **§3.2 Required members.** EC keys: `crv`, `kty`, `x`, `y`; RSA keys: `e`, `kty`, `n`. Optional
  members such as `kid`, `use` and `alg` are excluded. `DpopProofVerifier#import_public_key` drops
  `kid` before building the key, so a client that varies `kid` still yields the same thumbprint.
- **§3 (hash function and output).** A SHA-256 thumbprint is 32 bytes, 43 base64url characters without padding.
  `OpenidConnectAuthorizeForm::BASE64URL_SHA256_FORMAT` (`app/forms/openid_connect_authorize_form.rb`)
  validates `dpop_jkt` against that shape (`#validate_dpop_jkt`; companion EXC-19).
- **Use as a key identifier (§1, §6 security considerations).** A thumbprint identifies a public key
  but proves nothing by itself; possession is shown by a signature. Every thumbprint comparison here
  follows a verified signature: `DpopProofVerifier#call` computes the thumbprint only after the
  proof's signature verified, then compares it with `expected_thumbprint`; `OpenidConnectRefreshTokenForm#validate_refresh_token`,
  `OpenidConnectRevokeForm#owned?` and `OpenidConnectIntrospectForm#caller_entitled?` compare the
  verified proof's thumbprint with the stored binding.

## Deliberate choices and deviations

- **SHA-256 only.** RFC 7638 allows any hash; RFC 9449 §6.1 fixes SHA-256 for `jkt`, and the
  authorization request accepts only the 43-character form (D46 names the proof algorithms;
  the thumbprint hash follows RFC 9449).
- **The thumbprint, not the key, is stored.** `identities.dpop_jkt` and
  `token_exchange_tokens.dpop_jkt` hold the thumbprint; the public key arrives with every proof
  (`jwk` header) and is never persisted (companion §5.2 table, Appendix C "How it is built").
- **One thumbprint per family.** The exchange copies `identities.dpop_jkt` to the issuance record
  and refresh row; every refresh copies it forward unchanged
  (`OpenidConnectRefreshTokenForm#mint!`), so a family is bound to one key for its whole life (REF-3).
- **Replay scope.** The proof `jti` is recorded under the thumbprint (`ReplayGuard.first_use?`
  with `scope: thumbprint`), so two clients cannot burn each other's `jti` values.

## Questions this digest answers

- How is `dpop_jkt` computed by a client? base64url(SHA-256(canonical JSON of the required public members)); for P-256 that is `{"crv":"P-256","kty":"EC","x":"...","y":"..."}`.
- Does `kid` or `alg` in the `jwk` header change the thumbprint? No; only required members are hashed.
- Where does the server compute it? `DpopProofVerifier.thumbprint`, once per verified proof.
- What format is accepted on the authorization request? Exactly 43 base64url characters (`BASE64URL_SHA256_FORMAT`).
- Can a stolen thumbprint be used? No; it identifies the key, and every use requires a fresh signature from the private key.
- Where does an agency see it? In introspection as `cnf.jkt`, or as the `dpop_jkt` SAML attribute.
