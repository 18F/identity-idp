# RFC 8725 — JSON Web Token Best Current Practices

RFC 8725 collects the rules that keep JWT processing safe: never trust the `alg` header, pin the
algorithms, validate `iss`, `sub` and `aud`, type tokens explicitly, and do not trust received key
references. `ResourceServerAuthenticator` cites it as the hardening applied to RFC 7523 client
assertions; `DpopProofVerifier` follows the same rules for proofs. Canonical text: https://www.rfc-editor.org/rfc/rfc8725.txt

## Sections this implementation relies on

- **§3.1 Perform algorithm verification.** The recipient, not the `alg` header, decides which
  algorithms are acceptable; libraries must let callers pin them. `ResourceServerAuthenticator#verify_signature`
  (`app/services/resource_server_authenticator.rb`) passes `algorithm: 'RS256'` on every decode;
  `DpopProofVerifier#call` (`app/services/dpop_proof_verifier.rb`) checks the header `alg` against
  `ALLOWED_ALGORITHMS` and then pins that value on decode. Companion INT-6.
- **§3.2 Use appropriate algorithms.** `none` and weak or symmetric MACs are not acceptable where the
  verifier does not share a secret. Only `RS256` (assertions) and `ES256`/`RS256` (proofs) are accepted (D46).
- **§3.3 Validate all cryptographic operations.** Reject on any failure. Both verifiers return a
  failure result on `JWT::DecodeError` and never fall through to claim checks.
- **§3.8 Validate issuer and subject.** `#verify_signature` passes `iss:`/`verify_iss` and
  `sub:`/`verify_sub` so the library verifies both under the signature after `#unverified_issuer`
  used them for key selection.
- **§3.9 Use and validate audience.** `#audience_matches?` requires the endpoint's own URL; RFC 7523 digest.
- **§3.10 Do not trust received claims for key lookup.** `kid`, `jku`, `x5u` from the token must not
  be used to fetch keys blindly. The assertion's key is chosen by looking up the registered record
  for `iss`; the proof's key is inline and self-asserted, bound only by the stored thumbprint.
- **§3.11 Use explicit typing.** `typ` distinguishes kinds of JWT. The proof MUST be `dpop+jwt`
  (`DpopProofVerifier::PROOF_TYPE`); a client assertion is not accepted as a proof or the reverse.
- **§3.12 Mutually exclusive validation rules.** Different JWT kinds must not be confusable. The two
  credentials have different required claims, different key sources and separate `jti` namespaces
  (`ReplayGuard` `dpop:jti` and `client-assertion:jti`).
- **§2.7 Substitution attacks, §2.8 Cross-JWT confusion (with §3.9).** A JWT minted for one recipient must not be accepted by
  another; `aud` per endpoint URL prevents reuse of an assertion across the token, revocation and
  introspection endpoints.

## Deliberate choices and deviations

- **Signature before replay cache.** The `jti` is recorded only after the signature verified, so an
  anonymous party cannot burn a legitimate caller's values (both verifiers' class comments).
- **The authorization-code grant's looser assertion check is left as is**
  (`OpenidConnectTokenForm#validate_client_assertion`): no `jti`, optional `exp`. Hardening it is a
  separate decision so existing integrations are not affected (companion §6.1 "Why INT-6").
- **Unverified decode is limited to key selection**: `iss`/`sub` for assertions, the header for
  proofs; the payload read unverified is compared with the verified one for proofs.
- **`kid` is stripped from the proof key** rather than used for lookup (§3.10).

## Questions this digest answers

- Can a client choose `alg: ES256` for its client assertion? No; `RS256` is pinned.
- Can a proof use `alg: none` or `HS256`? No; refused before signature verification.
- Why is `typ: dpop+jwt` mandatory? Explicit typing (§3.11) and RFC 9449 §4.2.
- Does the server fetch keys from a `jku` in the token? Never.
- Why are `iss` and `sub` read before verifying? Only to find the record whose keys to verify with; both are re-verified under the signature.
- Why do the two credentials use different `jti` namespaces? So the same string cannot collide or be burned across kinds (§3.12).
