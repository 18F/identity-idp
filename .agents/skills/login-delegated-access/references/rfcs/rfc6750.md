# RFC 6750 — OAuth 2.0 Bearer Token Usage

RFC 6750 defines how a bearer token is presented to a protected resource (`Authorization: Bearer`)
and how the resource answers a bad or missing token (`WWW-Authenticate` with `invalid_token`). In
this repository it governs a confidential client's access token at userinfo and the error vocabulary
the DPoP scheme (RFC 9449 §7.1) reuses for a bound token. A confidential client's bearer request to
userinfo is unchanged by delegated access. Canonical text: https://www.rfc-editor.org/rfc/rfc6750.txt

## Sections this implementation relies on

- **§2.1 Authorization request header field.** `Authorization: Bearer <token>`.
  `AccessTokenVerifier#extract_access_token` (`app/services/access_token_verifier.rb`) splits the
  header into scheme and token and accepts `Bearer` or `DPoP` (`SCHEMES`); an unknown scheme or an
  empty token is `malformed_authorization`, as before.
- **§3 `WWW-Authenticate` response header.** A 401 for a protected resource carries a challenge with
  the scheme and optional `error`, `error_description`, `scope`. `AccessTokenVerifier#refuse`
  builds `DPoP algs="ES256 RS256", error="invalid_token"` (or `invalid_dpop_proof`) for a
  key-binding refusal, and `OpenidConnect::UserInfoController` and `OpenidConnect::DocumentImagesController`
  set it on the 401 (companion EXC-18 as built in §6.4).
- **§3.1 Error codes.** `invalid_request` (400), `invalid_token` (401), `insufficient_scope` (403).
  `invalid_token` is the code for a bound token presented as `Bearer` and for an unbound token
  presented as `DPoP` (`#verify_key_binding`); RFC 9449 §5 adds `invalid_dpop_proof` for a failing proof.
- **§5.2, §5.3 Threat mitigation.** Bearer tokens must be protected in transit and storage and
  should be short-lived; a stolen bearer token is usable by anyone. This is the gap the public
  client's DPoP binding closes (companion Appendix C.2) and why confidential clients, whose tokens
  never leave their servers, keep bearer tokens (D47).

## Deliberate choices and deviations

- **Delegated tokens are never valid bearer tokens at Login.gov's userinfo**, bound or not:
  `AccessTokenVerifier#load_identity` looks up `identities` only, and its comment forbids a second
  lookup path (EXC-6, INT-16). An agency presents a delegated token to its own API, which introspects it.
- **`token_type` tells the client which scheme to use**: `Bearer` for a confidential client's
  tokens, `DPoP` for a public client's, `N_A` for a SAML assertion (RFC 8693 §2.2.1).
- **The `DPoP` challenge is used even for an `invalid_token` refusal of a bearer-scheme request**,
  because the refusal concerns key binding and the challenge names the scheme and algorithms the
  client should have used (RFC 9449 §7.1).
- **Bearer identities are unchanged byte for byte**; the request spec compares a confidential
  client's response with and without a stray `DPoP` header (plan 5.6 item 9).

## Questions this digest answers

- Can an agency call userinfo with a delegated token? No; 401, with or without a proof (EXC-6).
- What header does a public client use at userinfo? `Authorization: DPoP <token>` plus a `DPoP` proof header.
- What does a bound token sent as `Bearer` get? 401 `invalid_token` with a `WWW-Authenticate: DPoP` challenge.
- Does anything change for a confidential client at userinfo? No.
- Where are the `invalid_token` strings? `openid_connect.user_info.errors.bound_token_requires_dpop` and `token_not_bound`.
- Is `insufficient_scope` used? Not by delegated access.
