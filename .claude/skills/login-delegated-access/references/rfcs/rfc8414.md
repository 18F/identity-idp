# RFC 8414 — OAuth 2.0 Authorization Server Metadata (with OpenID Connect Discovery 1.0)

RFC 8414 defines the metadata document an authorization server publishes and the names of its
members; OpenID Connect Discovery 1.0 defines the same document at `/.well-known/openid-configuration`
with OpenID Connect additions. Login.gov's discovery document advertises the delegated-access grants,
the introspection and revocation endpoints, their authentication methods and the DPoP algorithms,
but only while delegated access is switched on. Canonical texts:
https://www.rfc-editor.org/rfc/rfc8414.txt and https://openid.net/specs/openid-connect-discovery-1_0.html

## Sections this implementation relies on

- **RFC 8414 §2 Metadata members.** `grant_types_supported`, `token_endpoint_auth_methods_supported`
  (values from the RFC 7591 registry, `none` and `private_key_jwt` among them),
  `token_endpoint_auth_signing_alg_values_supported`, `revocation_endpoint` with its
  `_auth_methods_supported` and `_auth_signing_alg_values_supported`, and `introspection_endpoint`
  with the same two. `OpenidConnectConfigurationPresenter` (`app/presenters/openid_connect_configuration_presenter.rb`):
  `#grant_types_supported` adds `refresh_token` and `OpenidConnectTokenExchangeForm::GRANT_TYPE`;
  `#token_endpoint_auth_methods_supported` adds `none`; `#delegated_access_configuration` adds the
  six endpoint members. Companion DISC-1; D46, D48, E103.
- **RFC 8414 §2 (continued), RFC 7591 §2 `none`.** `none` means the client sends `client_id` without
  authenticating. Listed for the token, introspection and revocation endpoints because the
  public-client service provider calls all three with `client_id` and a DPoP proof (E103).
- **RFC 9449 §5.1 `dpop_signing_alg_values_supported`.** Advertised as
  `DpopProofVerifier::ALLOWED_ALGORITHMS` (`ES256`, `RS256`) (DISC-2; D46).
- **OpenID Connect Discovery §3 Provider metadata.** `issuer`, `authorization_endpoint`,
  `token_endpoint`, `userinfo_endpoint`, `jwks_uri`, `scopes_supported`, `claims_supported`,
  `acr_values_supported`, `subject_types_supported`, `id_token_signing_alg_values_supported`,
  `end_session_endpoint`. `#url_configuration` and `#crypto_configuration` are unchanged by delegated access.
- **RFC 8414 §2 Metadata describes what the server offers.** Members list the capabilities
  the server actually provides; a client relies on them to choose grants and endpoints. `#delegated_access_enabled?` gates
  every delegation member on `token_exchange_enabled`, so the document never names a grant the
  endpoint answers with `unsupported_grant_type` or an endpoint that returns 404 (DISC-5; D48).

## Deliberate choices and deviations

- **No `token_exchange_endpoint`**: RFC 8693 performs exchange at `token_endpoint`, and RFC 8414
  defines no such member (DISC-3).
- **`scopes_supported` is the static `VALID_SCOPES` list**; `token_exchange:*` values are per
  partner and are not enumerated (DISC-4).
- **No metadata for supported `requested_token_type` values**: none is standardized; the
  integration guide documents the formats (companion §15.6).
- **With the switch off the document is the pre-delegation document member for member**, pinned by
  the presenter spec against a literal (plan 5.11).
- **`token_endpoint_auth_methods_supported` gains `none` behind the same switch**, although DISC-1
  does not list it, because `none` is meaningful only once public clients can exchange (D48).

## Questions this digest answers

- Where is the exchange endpoint advertised? It is `token_endpoint`; there is no separate member.
- Why does discovery list `none`? For the public-client service provider's `client_id` plus DPoP calls (E103).
- Which algorithms does `dpop_signing_alg_values_supported` show? `ES256`, `RS256`.
- Why are the delegation members sometimes missing? `token_exchange_enabled` is off in that environment (DISC-5).
- Are `token_exchange:*` scopes in `scopes_supported`? No (DISC-4).
- Is there an SSF metadata change for the Attempts API? No (companion §5.4).

## When to fetch the full text

Read RFC 8414 §2 in full before adding a metadata member; check the IANA "OAuth Authorization Server
Metadata" registry for the exact name. https://www.rfc-editor.org/rfc/rfc8414.txt
