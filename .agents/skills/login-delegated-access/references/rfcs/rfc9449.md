# RFC 9449 — OAuth 2.0 Demonstrating Proof of Possession (DPoP)

RFC 9449 binds tokens to a public key the client holds: each request carries a short-lived signed
JWT (the proof) made for that method, URL and token, so a copied token is useless without the key.
In this repository binding follows the client type: every token issued to a public-client service
provider (its sign-in token, delegated tokens, refresh tokens, its authorization code) is bound,
and no token issued to a confidential client is. Login.gov verifies proofs at the token endpoint,
userinfo, revocation and introspection; agencies verify them on API calls using `cnf.jkt`.
Canonical text: https://www.rfc-editor.org/rfc/rfc9449.txt

## Sections this implementation relies on

- **§4.1 The `DPoP` header.** The proof travels in the `DPoP` request header. The token controller,
  `OpenidConnect::DelegatedEndpointConcern#form_params` (`app/controllers/concerns/openid_connect/delegated_endpoint_concern.rb`)
  and `OpenidConnect::UserInfoController` read `request.headers['DPoP']` only; a `dpop_proof` body field is not permitted.
- **§4.2 Proof JWT syntax.** Header `typ: dpop+jwt`, an asymmetric `alg`, `jwk` with the public key
  and no private members; payload `jti`, `htm`, `htu` (no query or fragment), `iat`, and `ath`
  (base64url SHA-256 of the access token) when a token accompanies the proof.
  `DpopProofVerifier` (`app/services/dpop_proof_verifier.rb`): `PROOF_TYPE`, `ALLOWED_ALGORITHMS`
  (`ES256`, `RS256`), `REQUIRED_CLAIMS`, `.token_hash`, `.normalize_url`. Companion EXC-9 as amended; D46.
- **§4.3 Checking proofs.** The numbered server checks: one header, well-formed JWT, required
  claims, `typ`, supported asymmetric `alg`, signature under the `jwk`, no private key, `htm`,
  `htu`, nonce (if issued), `iat` within an acceptable window, and for a protected-resource request
  `ath` and the key's thumbprint against the token's binding; `jti` SHOULD be tracked against replay.
  `DpopProofVerifier#call` runs them in that order, with the thumbprint comparison and the
  single-use `jti` (`ReplayGuard.first_use?`, `app/services/replay_guard.rb`) last so a rejected
  proof never consumes a `jti`. Appendix C "How it is built", E98.
- **§5 Token request.** A proof on the token request binds the issued access token; a refresh
  token issued to a public client MUST be bound to the key and refreshed with a proof from the same
  key; `token_type` is `DPoP`; a bad proof is the `invalid_dpop_proof` error.
  `OpenidConnectTokenForm#validate_dpop_proof` (`app/forms/openid_connect_token_form.rb`, no `ath`),
  `OpenidConnectTokenExchangeForm#validate_public_client_proof` (`ath` over the subject token,
  thumbprint equal to `identities.dpop_jkt`), `OpenidConnectRefreshTokenForm#validate_public_client_proof`
  and `#validate_refresh_token` (no `ath`; thumbprint equal to the family's `dpop_jkt`);
  `token_type` from `#issued_token_type_for`. EXC-17, REF-2 as amended.
- **§5.1 Server metadata.** `dpop_signing_alg_values_supported`.
  `OpenidConnectConfigurationPresenter#delegated_access_configuration`
  (`app/presenters/openid_connect_configuration_presenter.rb`), while delegated access is on (DISC-2).
- **§6, §6.1, §6.2 Public key confirmation.** The token is bound through `cnf.jkt`, the RFC 7638
  SHA-256 thumbprint; an introspection response carries `token_type: DPoP` and `cnf.jkt`.
  `OpenidConnectIntrospectForm#token_members` (`app/forms/openid_connect_introspect_form.rb`); INT-4, INT-9.
- **§7, §7.1 Protected resource access and the `DPoP` scheme.** The token is sent as
  `Authorization: DPoP <token>` with a proof carrying `ath`; a bound token presented with the
  `Bearer` scheme MUST be refused; the challenge is `WWW-Authenticate: DPoP` with `algs`.
  `AccessTokenVerifier#verify_key_binding` and `#refuse` (`app/services/access_token_verifier.rb`)
  for userinfo and document images; `OpenidConnectIntrospectForm#www_authenticate` for a failed
  proof at introspection. EXC-18. Companion §6.3 item 11 states the agency's obligation.
- **§10 Authorization code binding.** The `dpop_jkt` authorization request parameter binds the code
  to a key; the token endpoint checks the proof key against it.
  `OpenidConnectAuthorizeForm#validate_dpop_jkt` (`app/forms/openid_connect_authorize_form.rb`,
  required for a public client approved for delegation), stored on `identities.dpop_jkt`;
  `OpenidConnectTokenForm#validate_dpop_proof` compares. EXC-19, D21.
- **Security considerations, "DPoP Proof Replay" (cited as §11.1 in the project documents).**
  Servers SHOULD store `jti` values for the acceptance window. Kept for twice
  `dpop_proof_max_age_seconds` under the key thumbprint (`DpopProofVerifier#first_use_of_jti?`).

## Deliberate choices and deviations

- **No server nonce (§8, §9).** Freshness relies on `iat` within ±`dpop_proof_max_age_seconds`
  (300) and single-use `jti`. Rationale: D22 and E57 (an extra round trip through the browser client),
  E98 (the wide window compensates for partner clock skew; revisit if rejections appear).
- **Binding is a property of the client type**, not a per-API flag: `dpop_required` was dropped
  (D47). A confidential client never sends a proof; a public one always must (EXC-17).
- **`ath` only when a token is presented**: none at the code exchange or refresh (§4.3 item 12
  applies to access tokens), required at exchange (subject token), revocation and introspection
  (`token`), and userinfo. `ath` present without a token is refused.
- **Every proof problem is `invalid_dpop_proof`**, including a key mismatch at the code exchange;
  compare with the error §10 prescribes for a `dpop_jkt` mismatch before relying on this mapping.
  Only three failures get their own `error_description` (missing, key mismatch, replay); the rest
  share one, so the response does not help tune a forged proof.
- **`htu` normalization**: scheme and host lowercased, default port dropped, trailing slash
  ignored, query and fragment removed (`.normalize_url`), because `htu` behind proxies is the usual source of false rejections.
- **Introspection with a wrong-key proof is `{active: false}`**, not `invalid_dpop_proof` (D62).
- **SAML assertions carry the thumbprint as a `dpop_jkt` attribute** (E30), outside RFC 9449's scope.

## Questions this digest answers

- Which algorithms are accepted? `ES256` and `RS256`; never `none` or an HMAC (D46).
- How fresh must `iat` be? Within 300 seconds either side of now (`dpop_proof_max_age_seconds`).
- Does the exchange proof need `ath`? Yes, over the subject token. The refresh proof does not.
- Why was my proof rejected with no detail? Only missing, key-mismatch and replayed proofs are described; everything else is one message by design.
- Is `DPoP-Nonce` supported? No (D22, E57); do not send `nonce`.
- Can a confidential client send a proof? It is ignored for binding; its tokens are bearer (D47).
- What must the agency do with `cnf.jkt`? Verify a proof on every request and refuse `Bearer` for a bound token (§7.1; companion §6.3 item 11).
- Where does the `jti` replay cache live? Redis, keyed by namespace and a hash of thumbprint plus `jti` (`ReplayGuard`).
