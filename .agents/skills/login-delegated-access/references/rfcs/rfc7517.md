# RFC 7517 — JSON Web Key (JWK), with RFC 7518 key parameters

RFC 7517 defines the JSON representation of a cryptographic key; RFC 7518 §6 defines the
parameters for EC (`crv`, `x`, `y`, private `d`) and RSA (`n`, `e`, private `d`, `p`, `q`, `dp`,
`dq`, `qi`) keys. In this repository a JWK appears in the `jwk` header of every DPoP proof
(RFC 9449 §4.2) and is the input to the RFC 7638 thumbprint; Login.gov's own signing keys are
published at `jwks_uri` as before. Canonical texts: https://www.rfc-editor.org/rfc/rfc7517.txt and
https://www.rfc-editor.org/rfc/rfc7518.txt

## Sections this implementation relies on

- **RFC 7517 §4 JWK parameters.** `kty` REQUIRED; `use`, `key_ops`, `alg`, `kid`, `x5c` and others
  OPTIONAL. `DpopProofVerifier#import_public_key` (`app/services/dpop_proof_verifier.rb`) accepts a
  Hash, removes `kid` and builds a `JWT::JWK`; anything that fails to import is `dpop_proof_key`.
- **RFC 7518 §6.2 EC keys, §6.3 RSA keys.** The public members and the private members of each
  type. `DpopProofVerifier#call` refuses a `jwk` that includes private members (`jwk.private?`,
  `dpop_proof_private_key`), as RFC 9449 §4.2 and §4.3 item 7 require.
- **RFC 7518 §3.1 Algorithms.** `ES256` (ECDSA P-256 with SHA-256) and `RS256` (RSASSA-PKCS1-v1_5
  with SHA-256). `DpopProofVerifier::ALLOWED_ALGORITHMS` admits exactly these (D46); the key in
  `jwk` must match the algorithm or signature verification fails.
- **RFC 7517 §5 JWK Set.** The `keys` array served at `jwks_uri` (`api_openid_connect_certs_url` in
  `OpenidConnectConfigurationPresenter#url_configuration`); unchanged by delegated access.
- **RFC 7517 §9 Security considerations.** A key received from an untrusted party proves nothing by
  itself. The `jwk` in a proof is self-asserted; what makes it meaningful is that the same key
  (same thumbprint) must sign every later proof for the bound token (`DpopProofVerifier` class comment).

## Deliberate choices and deviations

- **The public key is never stored**; only its RFC 7638 thumbprint is (`identities.dpop_jkt`,
  `token_exchange_tokens.dpop_jkt`). Each proof brings the key again.
- **`kid` is ignored** so a client that labels its key differently across proofs still matches the
  stored thumbprint; the thumbprint excludes `kid` anyway (RFC 7638 §3.2).
- **No `x5c`, `jku` or `x5u` resolution**: the key must be inline in `jwk` (RFC 8725 §3.10, do not
  trust received key references).
- **Client assertion keys are not JWKs**: `ResourceServerAuthenticator#verify_signature`
  (`app/services/resource_server_authenticator.rb`) uses the X.509 certificates registered on the
  service provider or resource server record (`ssl_certs`), the same keys the authorization-code
  grant already uses.

## Questions this digest answers

- What must the `jwk` header contain? The public key only: `kty`, `crv`, `x`, `y` for P-256; `kty`, `n`, `e` for RSA.
- What if the proof's `jwk` includes `d`? Refused (`invalid_dpop_proof`).
- Does `kid` matter? No.
- Can a client register its DPoP key in advance? No; the key is self-asserted per proof and identified by thumbprint.
- Where are Login.gov's own keys? At `jwks_uri` (`/api/openid_connect/certs`), unchanged.
- Are client assertions verified against JWKs? No; against the registered certificates.
